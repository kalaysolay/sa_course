# AnalystGym — архитектура Java-приложения (v0.1)

Статус: предложена к обсуждению. После согласования — anchor для
поэтапного плана разработки и кодинга.
Связано: `docs/product-spec.md` (что строим), `docs/admin-guide.md`,
`TODO.md`, макет `tasks-mockup/` (прототип UX и контрактов).

## 0. Исходные ограничения

1. Соло-разработчик + AI-ассистент. Операционная сложность — главный враг:
   каждый сервис/брокер/кластер — это часы DevOps вместо фич.
2. Макет уже фиксирует UX и ключевые контракты (`ReviewResult`, рубрика,
   `Store` как прообраз API). Не перепроектируем, а переносим.
3. Два продукта с разной монетизацией, но один аккаунт, одна диагностика,
   общие справочники.
4. Деньги раньше идеала: архитектура должна позволить запустить MVP
   за 2–3 месяца part-time.

## 1. Стиль: модульный монолит (решение ADR-01)

Один деплоящийся артефакт, внутри — строгие модули:

```
backend/
  app/                 # Spring Boot entrypoint, конфиги, CORS, Host-роутинг
  modules/
    identity/          # пользователи, роли, JWT, сброс пароля
    catalog/           # задачи, подборки, справочники (метки/уровни)
    practice/          # черновики, попытки, решения
    review/            # пайплайн ревью, агенты, промпты, версии, A/B
    assessment/        # диагностика, подсчёт, планы прокачки
    courses/           # курсы, модули, уроки, прогресс, paywall
    content/           # импорт output/*.md, markdown, артефакты, файлы (S3)
    billing/           # заказы, подписки, владения, адаптер провайдера
    quality/           # жалобы, разборы, дашборд, студенты (read-модели)
    notify/            # письма/уведомления (заглушка → провайдер)
    admin/             # ревизии контента, лог действий (тонкий слой)
  shared/
    kernel/            # Result/ошибки, время, JSON, валидация
    persistence/       # Flyway-миграции, базовые репозитории
```

Правила (проверяются ArchUnit-тестом, когда заведём тесты):
- чужой пакет модуля трогать нельзя; общение — через facade + Spring Events;
- `review` не знает про HTTP; `catalog` не знает про LLM;
- циклических зависимостей между модулями нет.

**Швы будущего распила** (не пилим сейчас, но не замуровываем):
`review` (очередь + воркеры → отдельный сервис), `content` (S3 + импорт).

## 2. Стек

| Слой | Решение | Почему |
|---|---|---|
| Runtime | Java 21, Spring Boot 3.x, Gradle | Скорость разработки, найм, экосистема |
| БД | PostgreSQL 16 + Flyway | Рубрики/решения/рецензии — реляционные + JSONB для снапшотов |
| Кэш/лимиты/прогресс | Redis | Rate limit, SSE-pub/sub позже, кэш каталога |
| Очередь ревью | **Сначала таблица jobs в Postgres** (поллинг воркером) | Ноль новой инфраструктуры; RabbitMQ — когда упрёмся в объёмы |
| Файлы | Интерфейс Storage: сначала **файловая система** (VPS), S3-совместимое позже | MinIO жрёт RAM на маленьком VPS; интерфейс позволит переключить без правок |
| Фронтенд | **Гибрид (на согласовании):** статика макета сервится Boot'ом как есть + Thymeleaf в classpath для error-страниц, email-шаблонов и будущих SEO-страниц (см. ADR-02) | Не переписывать 40+ протестированных экранов; SSR — точечно, где нужен |
| LLM | Провайдеры конфигурируются в UI и переключаются на лету (см. §2.1) | Дефолт DeepSeek, запасные GLM/Qwen через провайдера; защита от «модель пропала» |
| Markdown | Рендер на клиенте (`md.js` уже есть и протестирован) | Сервер хранит сырой md, как сейчас `output/` |
| Почта | Thymeleaf-шаблоны + SMTP/Resend за интерфейсом | Нужна для сброса пароля и «ревью готово»; заодно и применение Thymeleaf из коробки |
| Reverse proxy | Caddy (авто-HTTPS) | Роутит `analystgym.ru/practice/course` на один app; различение по `Host` (параметр `product` уже есть в макете) |

### 2.1. LLM-провайдеры (переключаемые)

- Сущность `Provider`: название, `baseUrl` (OpenAI-совместимый), ссылка на
  ключ (vault/env, не в БД открытым текстом), список моделей, таймауты,
  включён/выключен, health-check кнопкой из админки.
- Привязка: агент → (провайдер, модель, запасной провайдер+модель).
  Дефолт на старте: DeepSeek (рабочее название `v4-pro` — уточнить точный
  ID модели при интеграции), запасные: GLM / Qwen через провайдера.
- Переключение — рантайм, без редеплоя (та же механика, что трафик версий
  промптов). Fallback-цепочка при ошибке/таймауте: primary → fallback →
  `failed` с инцидентом, не молча.
- Учёт стоимости: токены in/out на каждое ревью → в попытку и в дашборд;
  cost-cap на ревью с аварийным стопом.
- В админке (`#agents` + `#versions`): выбор провайдера/модели на агента,
  health-check, просмотр стоимости. В макете селект модели уже заложен
  (опция LLM заблокирована до подключения).

## 3. Модули: ответственность и границы

- **identity**: регистрация/вход (email+пароль), JWT access+refresh в httpOnly
  cookie, роли `STUDENT/METHODIST/REVIEWER/LLM_ADMIN/SUPERADMIN`, сброс пароля.
  Владеет: `users`, `roles`, `refresh_tokens`. Наружу: `CurrentUser`.
- **catalog**: CRUD задач/подборок/справочников (см. UC-M01–M09), workflow
  статусов, ревизии (каждое сохранение = revision с автором/временем —
  в макете это `taskEdits`, в Java — таблица ревизий). Наружу: read-модели
  для витрины (только `published`).
- **practice**: черновики, попытки, идемпотентный submit (`Idempotency-Key`
  на `POST /attempts` → 202 + `attemptId`). Хранит снапшот решения.
- **review** (ядро): job lifecycle (`queued → sa_running → arch_running →
  grading → done/failed`), вызов агентов последовательно, промпт — текст
  активной/canary-редакции по трафику %, ответ LLM валидируется по JSON-схеме
  `ReviewResult` (та же, что в макете), грейд считается **кодом** (веса),
  а не моделью. В попытку пишутся версии: рубрики, промптов, агента, движка.
  Прогресс — polling `GET /attempts/{id}` (SSE — позже).
- **assessment**: вопросы/варианты/веса/компетенции (CRUD в админке —
  сейчас захардкожены!), подсчёт (`scoring.js` → `AssessmentService`
  1-в-1), история замеров.
- **courses**: курсы/модули/уроки (CRUD нет в макете — добавить по образцу
  задач), контент lessons из `output/` через import-job (аналог
  `build-content.ps1`, но на сервере), прогресс, paywall/entitlements.
- **billing**: заказы, подписка Pro, владения курсами, адаптер провайдера
  (первый — ЮKassa под самозанятость), идемпотентные вебхуки, возвраты,
  промокоды (MVP: ручные коды).
- **quality**: read-модели (дашборд, топ miss), жалобы
  (`new → review → resolved/rejected` + резолюция), студенты.
- **notify**: события `review.done`, `password.reset`, реактивация;
  реализация позже, интерфейс сейчас.
- **admin**: тонкий слой поверх модулей + лог действий.

## 4. Пайплайн ревью (детально — это сердце продукта)

```
POST /attempts {taskId, tabs, Idempotency-Key} → 202 {attemptId: ...}
  → job row (payload: solution snapshot + rubricVersion + taskVersion)
  → worker: lock job (SKIP LOCKED)
  → for agent in [sa, arch] (порядок из конфига, выкл. агенты скипаются):
  │     promptText = resolve(agent.promptKey, traffic%)   // A/B здесь
  │     call LLM (JSON mode, schema ReviewResult/agent-part)
  │     validate → retry(1) → failed (жалоба-инцидент, не молча)
  → grade = code(weights) (как review-engine.coverageOf)
  → save attempt.review + versions {rubric, prompts, agents, engine}
  → event review.done → notify
GET /attempts/{id} → {status, progress, review?}   // polling 2s
```

Ограничения: таймаут агента 120с, cost-cap на ревью (счётчик токенов,
аварийный стоп), PII-скраб решения перед отправкой в LLM (минимум:
email/телефоны regex-ом — отдельным пунктом).

## 5. Данные (верхний уровень; детали — DDL при кодинге)

`users, roles` · `tasks (+revisions), criteria (в ревизии), collections,
collection_items, tags, levels` · `attempts (+solution snapshot),
reviews (+versions jsonb)` · `complaints` · `agents, prompts,
prompt_versions` · `assessments, assessment_answers, questions,
question_options` · `courses, modules, lessons, lesson_contents,
progress, entitlements` · `orders, subscriptions, payments, promo_codes` ·
`review_jobs` · `audit_log`.

Принципы: деньги и оценки — только append (никаких UPDATE поверх);
снапшот рубрики копируется в попытку (потом не «плывёт»); soft-delete
везде, где есть пользовательский контент.

## 6. Контентный конвейер (издательство → приложение)

1. Publisher пишет `output/<M>/<TOPIC>/{lecture,exercises,answers}.md`
   + `project/...` (как сейчас).
2. Import-job приложения (ручной запуск из админки + по крону):
   парсинг → валидация → новые ревизии lessons + артефактов в S3/БД →
   отчёт о diff.
3. `build-content.ps1` остаётся локальным fallback для статики;
   серверный импорт — его перенос 1-в-1.

## 7. Деплой и окружения

Целевое железо MVP: **VPS 4 CPU / 4 GB RAM**. Бюджет памяти (с запасом):
Postgres ~768MB (настроенный `shared_buffers`), Redis ~128MB, app
(`-Xmx1536m`), Caddy ~64MB, система ~512MB. Файловое хранилище вместо MinIO
(экономим ~300MB RAM и целый сервис). Swap 2GB как страховка. Сборка
(Gradle) на проде НЕ живёт — только рантайм.

- Локально: `docker compose up` (app, postgres, redis, caddy; minio —
  только профилем `full`, по умолчанию файлы на volume).
- Прод MVP, вариант A (рекомендую): **CI собирает образ → GHCR → на VPS
  `docker compose pull && up -d`**. Воспроизводимо, на VPS нет сборки,
  откат — предыдущий тег. Разовый сетап: GHCR-токен на сервере.
- Вариант B: `git pull + docker build` на VPS. Проще в голове, но сборка
  Gradle рядом с продом на 4GB — риск OOM; только с остановкой app
  на время билда. Запасной путь, если CI ляжет.
- Вариант C: fat-jar по scp + systemd (без Docker для app; postgres/redis
  всё равно нужны). Минимум оверхеда, максимум ручной работы. Не рекомендую
  первым.
- Поддомены: все на один app через Caddy; бренд/навигация по `Host`.
- Бэкапы: nightly `pg_dump` на диск VPS + недельная копия наружу
  (rclone в S3 — вторым этапом); restore проверять руками раз в месяц.
- CI (GitHub Actions): build → unit/integration (Testcontainers) →
  ArchUnit → образ в GHCR → (прод — вручную workflow_dispatch,
  без автодеплоя на каждый коммит).

## 8. Наблюдаемость и безопасность (минимум MVP)

- Structured logs (traceId = attemptId/runId), `/health`, метрики
  (Micrometer: время ревью, доля failed, стоимость LLM/ревью, воронка).
- Rate limits: submit ревью, диагностика, логин. OWASP basics: bcrypt/argon2,
  httpOnly cookies, CSRF, валидация загрузок, бэкапы с проверкой restore.
