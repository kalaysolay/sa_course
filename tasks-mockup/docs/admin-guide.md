# Руководство по админке AnalystGym (тренажёр)

Админка — `admin.html`. Всё, что здесь меняется, сразу влияет на продукт:
каталог, страницы задач, движок ревью. Отдельной кнопки «опубликовать» в макете
нет: сохранение = новая ревизия. Данные живут в `localStorage` браузера
(в продукте — таблицы + `updated_at` + автор правки).

Разделы идут в порядке рабочего дня методиста: задачи → проверка качества
(дашборд, решения, пользователи, жалобы) → инфраструктура ревью
(агенты, версии) → справочники → данные макета.

---

## 1. Задачи (`#tasks`) — главный экран

**Зачем.** Создание и редактирование задач: условие, рубрика, эталон,
принадлежность подборкам, жизненный цикл.

**Как работает.**
- Список: поиск, фильтры по уровню и статусу, смена статуса прямо из строки,
  средний балл и число попыток по каждой задаче, ссылка «глазами студента».
- Карточка: пять панелей-аккордеонов (Основное и Рубрика открыты, остальные
  свернуты). Сохранение пишет правки в `Store.taskEdits` поверх базовых данных.
- Новая задача: кнопка «+ Новая задача», ID генерируется из названия
  транслитом (`Идемпотентное списание` → `idempotentnoe-spisanie`, при коллизии
  `-2`, `-3`). Удаление — через «Сбросить правки» (для новой удаляет черновик).
- Статусы: `черновик → на ревью → опубликована → архив`. Студентам видна
  только опубликованная. Правка опубликованной = новая ревизия (в продукте —
  с changelog; в макете фиксируется только `updatedAt`).

**Где применяется.** Каталог (фильтры, сортировка), страница задачи
(условие, стартовые вкладки, подсказки, эталон), подборки (состав),
диагностика→план прокачки (метки), движок ревью (рубрика + веса).

**Чем заполняется.** Методистом вручную. Подсказки-плейсхолдеры в каждом
большом поле задают формат («Например: …»). Поля времени в MVP нет —
убрано сознательно.

## 2. Рубрика (внутри карточки задачи)

**Зачем.** Рубрика — это контракт оценки: за что даём баллы и как ищем
подтверждение в тексте решения.

**Как работает.** Критерий = название + вес 1–10 + зона (`sa`/`arch`) +
ключевые маркеры (синонимы через запятую) + `why` (объяснение «почему без
этого не работает», показываем студенту при miss) + флаг `critical`.
Скоринг: `hit` (≥2 маркеров) = полный вес, `partial` (1 маркер) = 55%,
`miss` = 0. Итог = 100 × набрано/сумма весов + структурный бонус
(диаграмма, числа, альтернативы — до ~18%). Пороги грейдов 1–5: 26/46/66/85.
Флаг `critical` зарезервирован под будущие штрафы (см. `TODO.md`):
miss по critical-критерию не даст подняться выше 3/5.

**Где применяется.** Движок ревью (`review-engine.js` → в продукте LLM):
покрытие критериев, тексты «учтено / не учтено», разбор в карточке ревью,
топ miss-критериев на дашборде.

**Чем заполняется.** Методистом. Проверка — симулятором ниже: вставил текст,
увидел балл и таблицу попаданий. Не сошлось — правишь маркеры или веса,
а не код.

## 3. Симулятор скоринга (внутри карточки задачи)

**Зачем.** Отладка рубрики без отправок: проверить, что эталон набирает
высоко, а пустое/поверхностное решение — низко.

**Как работает.** Берёт текст + текущую рубрику (включая несохранённые правки
из формы), прогоняет локальный движок, показывает балл, таблицу критериев
(учтено/частично/не учтено + найденные маркеры) и оценки агентов.
Кнопка «Подставить эталон» — быстрый regression-тест рубрики.

## 4. Дашборд (`#dashboard`)

**Зачем.** Утренний обзор здоровья тренажёра: что горит, что чинить.

**Как работает.**
- KPI: опубликовано задач, попыток студентов, средний балл, новых жалоб.
- «Требуют внимания»: задачи с открытыми жалобами + задачи со средним баллом
  ниже 50. Клик ведёт в карточку задачи.
- «Топ miss-критериев»: какие критерии валят чаще всего по реальным попыткам.
  Если один критерий валят все — чинить надо рубрику/подсказку, а не студентов.
- «Последние жалобы» с переходом в очередь.

**Чем заполняется.** Автоматически: попытки студентов + очередь жалоб.
Пустые состояния честно говорят, чего не хватает («отправьте пару решений»).

## 5. Решения (`#attempts`)

**Зачем.** Разбор «решение рядом с ревью» — главный инструмент понимания,
где тюнить: рубрику, промпт или эталон.

**Как работает.** Таблица всех попыток (дата, задача, балл, критерии
`закрыто/всего`, оценки агентов, статус) с фильтром по задаче. Кнопка
«Разбор» открывает модалку: слева текст решения студента (+ число диаграмм),
справа — ревью (агенты, критерии hit/miss), внизу — ссылки «Рубрика задачи»
и «Задача глазами студента».

**Чем заполняется.** Попытками студентов (в макете — из этого браузера).

## 6. Пользователи (`#users`)

**Зачем.** Контекст автора при разборе решений и жалоб: кто жалуется —
джун после 3 попыток или сеньор с баллом 82.

**Как работает.** В макете — 6 демо-студентов (бейдж «демо») с ролью, уровнем,
попытками, средним баллом, активностью. Карточка: последние попытки со
ссылками на задачи. В продукте здесь живые пользователи + диагностика +
заметки методиста.

## 7. Жалобы (`#complaints`)

**Зачем.** Очередь споров «студент vs ревью» — главный источник сигналов
для тюнинга. Каждая разобранная жалоба заканчивается либо правкой
(рубрика/промпт/подсказка), либо ответом студенту — оба исхода фиксируются.

**Как работает.** KPI по статусам (`Новая → Разбираем → Решена/Отклонена`),
фильтр, таблица (причина, задача, студент, балл, версия промпта, дата).
Карточка: фрагмент решения + причина спора + итог разбора (текстовое поле),
кнопки смены статуса, ссылки в рубрику и на задачу. В макете 4 сида.

## 8. Агенты (`#agents`)

**Зачем.** Управление двумя ревьюерами: кто они, что проверяют, на каком
промпте работают, кто в пайплайне.

**Как работает.** Карточка агента: аватар, имя, роль, фокус проверки
(редактируется — по строке на проверку; этот же список видит студент),
модель (`mock-agents/v1`; LLM — после подключения), связанный промпт
с активной версией, тумблер участия в пайплайне. Выключение в макете —
флаг состояния; в продукте исключает агента из цепочки ревью.

## 9. Версии (`#versions`)

**Зачем.** Версионирование и A/B инфраструктуры оценки. Железное правило:
каждое выданное ревью знает версию промпта — иначе тюнинг вслепую.

**Как работает.**
- **Промпты.** Карточка промпта: ключ, агент, таблица редакций (v, статус,
  трафик %, дата, changelog, модель). Трафик правится числом — сумма по
  промпту должна быть 100%. Кнопка «Сделать активной» (с подтверждением)
  переводит 100% трафика на версию, остальные — в архив. Статусы:
  `active` (в проде), `canary` (эксперимент на доле трафика), `archived`.
- **Новая версия.** Кнопка «+ Новая версия»: номер подставляется сам
  (max+1), текст копируется из выбранной редакции или пишется с нуля,
  changelog обязателен (без него версию не отличить), стартовый трафик
  0 = в архив, >0 = сразу канарейка.
- **Текст версии.** Кнопка «Текст» в строке редакции (точка • — текст задан).
  Плейсхолдеры: `solution`, `rubric`, `task_title`, `criteria`. Честно:
  в макете текст хранится, но mock-движок его не читает (читает рубрику);
  текст заработает с LLM-пайплайном — зато версионирование, трафик
  и promote работают уже сейчас.
- **Что такое трафик.** Доля запросов на ревью, уходящая на эту редакцию.
  Пример: `sa-reviewer v3 — 80%`, `v4 (canary) — 20%`. Каждый пятый студент
  оценивается экспериментальной редакцией; сравниваем баллы и жалобы v3 vs v4
  и либо promoted v4 (100%), либо откатываем. Канарейка — способ менять
  поведение ревью без ставки «всё или ничего».
- **Ревизии рубрик.** Таблица по задачам: число критериев, v1/v2 (есть правки
  из админки или нет), дата обновления, ссылка в карточку. В продукте здесь
  же — привязка «попытка → версия рубрики».

**Чем заполняется.** Методистом (новые редакции — в продукте отдельным
редактором; в макете правятся в данных + changelog вручную).

## 10. Справочники: метки, уровни, подборки

**Зачем.** Контролируемые словари, на которых держатся фильтры каталога,
план прокачки и состав подборок.

**Как работает.**
- Метки: название, ID, категория, синонимы (для поиска), вкл/выкл.
  Выключенная метка остаётся на задачах, но исчезает из фильтров.
  Удаление занятой метки запрещено (сломает фильтры) — только скрытие.
- Уровни: название, цвет, профиль кандидата, ориентир по времени. Удалять
  нельзя (на них завязаны задачи и план прокачки).
- Подборки: название, описание, иконка, упорядоченный состав задач,
  видимость. Одна задача может входить в несколько подборок.

## 11. Данные макета (`#data`)

**Зачем.** Служебный раздел: что лежит в `localStorage`, экспорт состояния
в JSON, полный сброс демо-данных, состав контента (счётчики задач,
критериев, меток, вопросов).

## Глоссарий (коротко)

- **Рубрика** — список критериев задачи с весами. Контракт оценки.
- **Вес 1–10** — максимум баллов за критерий. Итог = 100 × набрано/сумма.
- **Critical** — флаг «без этого выше 3/5 никак» (механика штрафов — в TODO).
- **Hit / partial / miss** — найдены ≥2 маркера / 1 маркер / ни одного.
- **Ревизия** — сохранённая правка задачи/рубрики/промпта. В макете = факт
  сохранения; в продукте — версия с changelog и автором.
- **Трафик (A/B)** — % запросов на конкретную редакцию промпта.
- **Canary** — экспериментальная редакция на малой доле трафика.
- **Симулятор** — прогон текста через движок с разбором по критериям.
- **Miss-топ** — критерии, которые валят чаще всего; сигнал чинить контент.
