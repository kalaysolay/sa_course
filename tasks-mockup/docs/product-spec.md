# AnalystGym — спецификация продукта (основа Java-приложения)

Версия: 0.1 (по состоянию макета `tasks-mockup/`).
Статус: рабочий документ. Макет — кликабельный прототип UX и поведения;
этот документ фиксирует, ЧТО строим, для КОГО и КАК должно работать.

Связанные документы: `docs/admin-guide.md` (админка), `TODO.md` (отложенное),
`README.md` (карта макета и поддоменов).

---

## 1. Цели проекта

### 1.1. Бизнес-цели
1. **Выручка с двух продуктов:** подписка тренажёра (Pro, помесячно/год) +
   разовые покупки курсов. Цель MVP: первые 100 платящих за 6 месяцев.
2. **Дешёвое привлечение:** бесплатная диагностика уровня как магнит
   (цель: ≥30% посетителей хаба проходят диагностику).
3. **Удержание через прогресс:** студент видит измеримый рост (повторная
   диагностика, баллы ревью, % прохождения) — цель: ≥40% вернувшихся
   в течение 14 дней после первого ревью.

### 1.2. Продуктовые цели
1. Готовить к собеседованию **практикой, а не теорией**: решение пишется
   как на работе, разбирается как на собесе.
2. Оценка — **качество решения, а не «верно/неверно»**: что учтено,
   что упущено, почему (не) сработает, что спросят дальше.
3. Методист правит контент без разработчиков: задачи, рубрики, промпты,
   подборки — всё через админку с версионированием.
4. Каждое ревью воспроизводимо: известно, какая версия рубрики, промпта
   и агента его выдала (иначе невозможен тюнинг).

### 1.3. Не-цели MVP
Мобильные приложения, маркетплейс авторов, live-менторство, LMS-интеграции
(SСORM/xAPI), мультиязычность (только RU), офлайн-режим.

## 2. Описание продукта

### 2.1. Состав
| Продукт | Домен (прод) | Макет | Суть |
|---|---|---|---|
| Хаб-развилка | `analystgym.ru` | `index.html` | Два полуэкрана (Практика / Курсы) + магнит-диагностика, без шапки/подвала |
| Тренажёр (Practice) | `practice.analystgym.ru` | `practice.html`, `catalog.html`, `collections.html`, `task.html`, `assessment.html`, `results.html` | Задачи с ревью ИИ-агентов + диагностика |
| Курсы (Course) | `course.analystgym.ru` | `courses.html`, `course.html` | Уроки по модулям, прогресс, разовая оплата |
| Админка | внутр. | `admin.html` | Задачи, качество (дашборд/решения/пользователи/жалобы), агенты, версии, справочники |

### 2.2. Акторы и роли
- **Гость** — видит хаб, каталоги, бесплатный контент; решения и диагностика
  требуют... (в MVP без регистрации, состояние в браузере; в Java — аккаунт).
- **Студент** — зарегистрированный пользователь: решения, попытки, прогресс
  курсов, диагностика, жалобы.
- **Методист** — создаёт и правит задачи, рубрики, подборки, справочники;
  разбирает жалобы; правит контент, не код.
- **Ревьюер качества** — разбирает попытки и жалобы, подтверждает ревью
  (роль заложена в модель, отдельный экран — позже).
- **Админ LLM-инфраструктуры** — агенты, промпты, версии, трафик A/B.
- **Супер-админ** — роли доступа, лог действий (заложено, экраны — позже).
- **Система** — пайплайн ревью, подсчёт диагностики, фоновые сверки.

### 2.3. Ключевые принципы
1. Рубрика — контракт оценки; текст рубрики виден студенту (кроме эталона).
2. Эталон виден только после ревью.
3. Правка опубликованного = новая ревизия, тихо не правим.
4. Студентам виден только статус `опубликована`.
5. Диагностика — магнит в контенте, не пункт навигации.
6. Продукты разделены (свои навигации, своя монетизация), связаны
   кросс-ссылками, общим аккаунтом и диагностикой.
7. Логотип везде ведёт на хаб платформы (`index.html`), а не на главную
   продукта; из футеров обоих продуктов есть ссылка «AnalystGym — платформа».
8. Мобильная навигация: на ≤860px меню сворачивается в бургер (выпадашка,
   закрытие по ссылке/мимо/Escape); шапка ужата (у кнопки темы остаётся
   только значок). Favicon (`logo.png`) подключён на всех страницах.

## 3. Юзкейсы

Формат: предусловия → шаги → исключения → постусловия → привязка к макету
(что переиспользовать при кодинге).

### 3.1. Студент — тренажёр

#### UC-S01. Просмотр каталога задач
- **Предусловия:** нет.
- **Сценарий:** 1. Открыть каталог. 2. Фильтровать по уровню/меткам/статусу,
  искать, сортировать. 3. Открыть задачу. Фильтры — в URL (ссылки шарингуются).
- **Постусловия:** —. **Макет:** `catalog.html`, `catalog.js`.

#### UC-S02. Прохождение подборки
- **Сценарий:** 1. Открыть подборку (домен). 2. Видеть состав, уровни,
  свой прогресс. 3. Кнопка ведёт на первую нерешённую задачу.
- **Макет:** `collections.html`.

#### UC-S03. Написание решения
- **Сценарий:** 1. Слева условие (включая критерии оценки — что спросят).
  2. Справа вкладки: документ (WYSIWYG), PlantUML, Mermaid (+добавить/
  переименовать/дублировать/закрыть). 3. Диаграммы рендерятся живьём.
  4. Черновик автосохраняется. 5. Подсказки открываются по одной, эталон
  скрыт до ревью.
- **Исключения:** E1 — пустое решение: отправка разрешена, но с
  предупреждением в диалоге подтверждения.
- **Макет:** `task.html`, `task.js`.

#### UC-S04. Отправка решения на ревью
- **Предусловия:** черновик существует.
- **Сценарий:** 1. «Отправить решение» → диалог со сводкой (вкладки, слова,
  диаграммы). 2. Подтвердить. 3. Видеть живой прогресс двух агентов
  (стадии проверки). 4. Автоскролл к готовому ответу.
- **Постусловия:** попытка сохранена со статусом, затем с ревью; черновик цел.
- **Макет:** `task.js` (askSubmit/submit/startReview), `review-engine.js`.

#### UC-S05. Просмотр ревью
- **Сценарий:** 1. Вердикт: грейд 1–5 + балл/100 + расшифровка «почему».
  2. Два агента: оценка/10, «учтено» (с цитатами из решения), «не учтено»
  (с объяснением последствий), нарратив «почему (не) решает задачу»,
  «как усилить», вопросы интервьюера. 3. Разбор по критериям рубрики.
  4. «Что потренировать дальше» (ссылки на задачи).
- **Макет:** `task.js` (renderReview), структура `ReviewResult` в движке.

#### UC-S06. История и повторные попытки
- **Сценарий:** список попыток с баллами, переключение между ревью,
  «Доработать и отправить снова». Динамика баллов видна.
- **Макет:** `#attemptsSection` в `task.js`.

#### UC-S07. Просмотр эталона
- **Предусловия:** есть хотя бы одно ревью по задаче (иначе — спойлер
  убивает тренировку).
- **Сценарий:** раскрыть «Эталонное решение автора» (документ + схемы).
- **Макет:** `#authorFold` в `task.js`.

#### UC-S08. Оспаривание ревью (жалоба)
- **Сценарий:** 1. Кнопка «Оспорить» в карточке ревью. 2. Причина текстом.
  3. Жалоба уходит в очередь админки со ссылкой на попытку, задачу
  и версию промпта.
- **Постусловия:** жалоба в статусе «Новая». **Макет:** частично (очередь
  и разбор есть в админке; кнопку в карточке ревью добавить).

### 3.2. Студент — диагностика

#### UC-D01. Прохождение диагностики
- **Сценарий:** 40 вопросов, один на экран; навигация стрелками/цифрами/точками,
  флаг «сомневаюсь», автопереход после ответа, возврат и правки, выход
  с сохранением прогресса, подтверждение при пропусках/завершении.
- **Постусловия:** результат посчитан и сохранён.
- **Макет:** `assessment.html`, `assessment.js`, `scoring.js`.

#### UC-D02. Просмотр результата
- **Сценарий:** грейд + балл, кольцо, профиль по 7 компетенциям (сильные зоны
  / пробелы), интерпретация, «взгляд работодателя», план прокачки
  (задачи под пробелы), разбор каждого ответа, копирование результата.
  Кнопка «К задачам по моему уровню» ведёт в каталог с предустановленными
  метками двух главных пробелов (`catalog.html?tag=...`), а не в общий список.
- **Макет:** `results.html`, `results.js` (levelCatalogUrl).

#### UC-D03. Повторная диагностика
- **Сценарий:** перепройти в любой момент; прошлый результат виден до старта;
  новый перезаписывает (история замеров — в продукте).
- **Макет:** `assessment.html` (блок «Предыдущая диагностика»).

### 3.3. Студент — курсы

#### UC-C01. Каталог курсов
- **Сценарий:** карточки (лого, название, цена/скидка/бесплатно, длительность,
  уровень, прогресс, CTA по состоянию).
- **Макет:** `courses.html`, `courses.js`.

#### UC-C02. Страница-обзор курса
- **Сценарий:** описание, outcomes, мета, программа по модулям, цена,
  CTA («Начать/Продолжить/Пройти заново» → нужный урок).
- **Правило:** `course.html?id=X` без `&lesson=` — всегда обзор.
- **Макет:** `course.js` (renderAbout).

#### UC-C03. Прохождение урока
- **Сценарий:** сайдбар модулей (счётчики, текущий подсвечен и подкручен
  в видимость), контент, виды «Лекция / Упражнения / Артефакты» (переключатель
  в шапке + диплинки `?view=`), ответы под катом, отметка «пройден»,
  навигация prev/next.
- **Макет:** `course.html`, `course.js`, `md.js`, контент из `output/`.

#### UC-C04. Демо-доступ и покупка
- **Сценарий:** неоплаченные уроки показывают paywall (цена, что входит).
  «Оформить» → оплата (в продукте) → доступ ко всем урокам. В макете —
  демо-разблокировка в один клик.
- **Макет:** paywall + `#buyBtn` в `course.js`.

#### UC-C05. Прогресс курса
- **Сценарий:** счётчик и бар в шапке курса, статусы уроков (✓/🔒/номер),
  прогресс на карточке каталога.
- **Макет:** `Store.courseProgress`, `courses.js`, `course.js`.

### 3.4. Методист — контент

#### UC-M01. Создание задачи
- **Сценарий:** «+ Новая задача» → название → ID генерируется транслитом
  (уникализация `-2`, `-3`) → статус `черновик` → заполнение → сохранить.
- **Макет:** `admin-tasks.js` (blankTask, slugify).

#### UC-M02. Редактирование задачи
- **Сценарий:** пять аккордеонов (Основное, Условие, Рубрика, Контент+эталон,
  Симулятор). Сохранение = новая ревизия, сразу влияет на продукт
  (в Java — через workflow публикации, см. UC-M04).
- **Макет:** `admin-tasks.js` (renderCard/collectForm).

#### UC-M03. Управление рубрикой
- **Сценарий:** CRUD критериев: название, вес 1–10, зона sa/arch, маркеры,
  `why`, флаг critical. Проверка — симулятором (UC-M05).
- **Макет:** paintRubric/collectRubric.

#### UC-M04. Жизненный цикл задачи
- **Сценарий:** смена статуса `черновик → на ревью → опубликована → архив`
  (из списка или карточки). Студентам видна только опубликованная.
  Архивная пропадает из каталога, история попыток сохраняется.
- **Макет:** статусные селекты, `Store.taskStatus`.

#### UC-M05. Симулятор скоринга
- **Сценарий:** вставить текст (или подставить эталон) → «Проверить» → балл
  + таблица попаданий по критериям + оценки агентов. Используется для
  отладки рубрики до публикации.
- **Макет:** панель симулятора, `ReviewEngine.buildReview`.

#### UC-M06. Управление подборками
- **Сценарий:** CRUD подборки: название, описание, иконка, упорядоченный
  состав (чекбоксы в карточке задачи двусторонне синхронизируются),
  видимость.
- **Макет:** существующий раздел «Подборки».

#### UC-M07. Справочники (метки, уровни)
- **Сценарий:** CRUD меток (название, ID, категория, синонимы, вкл/выкл);
  уровни — переименование/описание без удаления. Скрытие вместо удаления
  занятых меток. Поиск по меткам, выбранные — первые.
- **Макет:** разделы «Метки», «Уровни».

#### UC-M08. Превью глазами студента
- **Сценарий:** из списка/карточки — открыть задачу как её видит студент.
- **Макет:** ссылки `task.html?id=`.

#### UC-M09. Импорт/экспорт задач (JSON)
- **Сценарий:** выгрузка задачи/каталога в JSON (наполнение, бэкап, перенос
  между стендами); загрузка с валидацией схемы.
- **Макет:** частично (экспорт состояния в «Данных макета»); полный — в Java.

### 3.5. Качество

#### UC-Q01. Дашборд
- **Сценарий:** KPI, «Требуют внимания» (жалобы + просевшие баллы → в задачи),
  топ miss-критериев (сигнал чинить контент), последние жалобы.
- **Макет:** `admin-ops.js` (renderDashboard).

#### UC-Q02. Разбор попытки
- **Сценарий:** фильтр по задаче → таблица попыток → модалка «решение рядом
  с ревью» (текст, диаграммы, агенты, критерии) → переходы в рубрику/задачу.
- **Макет:** renderAttempts/openAttemptModal.

#### UC-Q03. Разбор жалобы
- **Сценарий:** очередь с фильтром статусов → карточка (фрагмент решения,
  причина, версия промпта) → итог разбора → статус
  (`Новая → Разбираем → Решена/Отклонена`) → ссылки в рубрику/задачу.
- **Макет:** renderComplaints/openComplaintModal.

#### UC-Q04. Карточка студента
- **Сценарий:** список (роль, уровень, попытки, средний балл, активность) →
  карточка с последними попытками. Контекст для разбора жалоб.
- **Макет:** renderUsers (демо-данные).

### 3.6. LLM-инфраструктура

#### UC-L01. Управление агентами
- **Сценарий:** карточка агента (имя, роль, фокус — редактируется построчно,
  модель, связанный промпт с активной версией), тумблер участия в пайплайне.
- **Макет:** renderAgents, `Store.agents/saveAgent`.

#### UC-L02. Редактирование текста промпта
- **Сценарий:** кнопка «Текст» в строке версии → редактор с подсказкой
  плейсхолдеров (`solution`, `rubric`, `task_title`, `criteria`) → сохранить.
- **Макет:** data-version-text модалка.

#### UC-L03. Новая версия промпта
- **Сценарий:** «+ Новая версия» → номер авто (max+1), копирование текста
  из выбранной, обязательный changelog, стартовый трафик (0 = архив,
  >0 = канарейка) → создать.
- **Макет:** data-new-version модалка, `Store.addPromptVersion`.

#### UC-L04. Управление трафиком A/B
- **Сценарий:** число % в строке версии, сумма по промпту = 100%.
  Канарейка → сравнение баллов/жалоб → promote или откат.
- **Макет:** data-traffic, `Store.setPromptTraffic`.

#### UC-L05. Promote версии
- **Сценарий:** «Сделать активной» → подтверждение → 100% трафика,
  остальные в архив, текст/changelog не затираются.
- **Макет:** data-promote, `Store.promotePrompt`.

#### UC-L06. Ревизии рубрик
- **Сценарий:** таблица по задачам (критериев, v1/v2, дата) → переход
  в рубрику. В Java: привязка «попытка → версия рубрики».
- **Макет:** таблица в разделе «Версии».

### 3.7. Администрирование (заложено)

#### UC-A01. Роли доступа
- Методист (контент), ревьюер (жалобы/попытки), LLM-админ (агенты/промпты),
  суперадмин (роли, лог). В макете один доступ; модель готова.

#### UC-A02. Оформление
- Три темы (тёмная/серая IDE/светлая), выбор в шапке, хранение локально.
  В Java — настройка профиля.

### 3.8. Системные (фоновые)

#### UC-SYS01. Выдача ревью
- **Сценарий:** accepted-задача → стадии двух агентов (по фокусу и промпту
  активной/canary-редакции по трафику) → грейд → сохранение попытки
  с версиями (рубрика, промпты, агент, движок).
- **Макет:** `ReviewEngine.runReview/buildReview`.

#### UC-SYS02. Диагностика и план
- **Сценарий:** подсчёт взвешенного балла, грейд, профиль 7 компетенций,
  сильные/слабые зоны, план из задач под пробелы.
- **Макет:** `scoring.js` (compute/buildPlan/narrative/marketView).

## 4. Модель данных (кратко, детали — в коде макета)

- **Task**: id, title, level→Level, tags[]→Tag, statement{brief,context,goal,
  inputs,deliverables,constraints,interview}, starterTabs[], rubric:
  Criterion{id,title,weight 1–10,focus,keywords[],why,critical}, hints[],
  interviewQuestions[], authorSolution{doc}, status, timeMin, createdAt,
  updatedAt, stats (derived).
- **Collection**: id, title, tagline, description, icon, audience,
  taskIds[] (ordered), active.
- **Tag / Level / Competency / Grade**: справочники (`data-core.js`).
- **Attempt**: id, taskId, userId, submittedAt, status, tabs[] (решение),
  review: **ReviewResult** {grade, summary, why[], criteria[{state,
  matched[],evidence}], agents[{score,covered[],missed[],narrative,
  improve[],questions}], stats, engine, rubricVersion, promptVersions}.
- **Complaint**: id, taskId, attemptId?, userId, score, reason, excerpt,
  promptVersion, status, resolution, createdAt.
- **User**: id, name, role (SA/BA), level, stats (derived).
- **Agent**: id, name, role, initials, checks[], model, enabled,
  promptKey.
- **Prompt**: key, name, agent; **PromptVersion**: v, status
  (active/canary/archived), traffic %, text, changelog, model, updatedAt.
- **Course/Lesson**: course{id,title,price,modules[{sections[{lessons[]}]}]},
  progress per user, owned (paywall).
- **Assessment**: answers{qId:option}, flags, result{score, grade,
  byCompetency[], strengths, gaps, detail[]}.

Прототипы структур: `assets/js/data-*.js` (данные), `store.js` (состояние
и слияния), `review-engine.js` (контракт `ReviewResult` — главный кандидат
в DTO Java-бэка).

## 5. Нефункциональные требования (MVP)

1. Время ответа каталога/задачи p95 ≤ 500 мс (без ревью); ревью — асинхронно,
   прогресс виден живьём, результат переживает перезагрузку.
2. Ревью идемпотентно по попытке; повторная отправка не плодит ревью.
3. Все мутации контента — через ревизии с автором и временем.
4. Персданные: минимум (имя, контакт для оплаты), удаление по запросу.
5. Оплата (вне ядра MVP, интерфейс): провайдер за адаптером; валюты RUB/KZT;
   webhooks идемпотентны.
6. Стек-ориентир: Java 21, Spring Boot, PostgreSQL (+Flyway), S3-совместимое
   хранилище для `output/`-контента, очередь под пайплайн ревью.
