# Требования к Compliance API / контракт API

Статус: начальная каноническая версия, подготовлена в уроке 42 `INT-API-DESIGN`  
Владелец содержания: системный аналитик Compliance Platform  
Согласующие: команда Employee Portal, разработка и QA Compliance  
Дата начальной версии: 2026-08-28

## Назначение и граница достоверности

Контракт описывает учебное взаимодействие Employee Portal и Compliance Platform при создании и чтении декларации о подарке. Его бизнес-цель — зафиксировать одну декларацию на одно намерение сотрудника, вернуть наблюдаемый идентификатор и статус и не создать дубль при повторе после тайм-аута.

Первичные предметные источники для темы не зарегистрированы, каталог авторских материалов пуст, а внешнее исследование для run запрещено. Поэтому пути, имена полей, логические коды и роли ниже являются проектными решениями начальной версии, а не сведениями о работающем production API. Пункты с пометкой «Открыто» требуют подтверждения владельцев.

## Участники и ответственность

| Роль | Участник | Ответственность |
| --- | --- | --- |
| Инициатор | Сотрудник | Выражает намерение создать декларацию и получает понятный результат |
| Consumer | Employee Portal | Передаёт минимальные данные, сохраняет `intentId`, обрабатывает результат и не создаёт новый intent при техническом повторе |
| Provider | Compliance API / Compliance Platform | Проверяет субъект, права и бизнес-правила, меняет состояние, сохраняет диагностический след и возвращает согласованный результат |
| Владелец данных | Предварительно Compliance Platform | Владеет смыслом декларации и её статусов; требует подтверждения product owner |
| Дополнительный consumer | Рабочее место комплаенс-офицера | Читает только назначенный и разрешённый объём данных |

Граница provider проходит по Compliance API. Consumer не записывает декларацию напрямую в хранилище Compliance и не выводит бизнес-успех из факта отправки запроса.

## Бизнес-сценарий и состояния

1. Сотрудник заполняет обезличенную форму и нажимает «Отправить».
2. Portal создаёт один `intentId` для этого бизнес-намерения.
3. Compliance API распознаёт субъект, проверяет право и допустимость данных.
4. Provider создаёт одну декларацию либо находит прежний результат того же `intentId`.
5. Portal получает `declarationId` и `status` и показывает их сотруднику.
6. При потерянном ответе Portal сообщает о неизвестном исходе, а затем проверяет результат или повторяет вызов с тем же `intentId` по договору.

Учебный успешный статус — `SUBMITTED`. Полный жизненный цикл, допустимые переходы и возможность исправления полей — открытые вопросы; этот документ не заменяет state model.

## Операция 1. Создать декларацию

### Карточка операции

| Атрибут | Решение начальной версии |
| --- | --- |
| Логическое имя | `CreateGiftDeclaration` |
| Условное отображение | `POST /gift-declarations` |
| Consumer / provider | Employee Portal / Compliance API |
| Цель | Создать одну декларацию о подарке на одно намерение |
| Предусловия | Субъект распознан; право создать декларацию от своего имени подтверждено; обязательные данные допустимы; передан `intentId` |
| Изменение состояния | Создаётся одна декларация либо возвращается прежний результат того же намерения |
| Успех | `declarationId`, `status`, `createdAt`, `correlationId` |
| Идемпотентность | Тот же `intentId` и тот же смысловой запрос не создают новую декларацию |
| Конфликт | Тот же `intentId` с иным смысловым содержимым отклоняется как `INTENT_CONFLICT` |

### Учебный запрос

```json
{
  "intentId": "INTENT-EXAMPLE-001",
  "employeeRef": "EMP-ANON-001",
  "giftCategory": "OTHER",
  "giftDate": "2026-08-20",
  "amount": {
    "value": "125.00",
    "currency": "KZT"
  },
  "description": "Обезличенный учебный пример"
}
```

| Поле | Смысл | Обязательность и ограничение |
| --- | --- | --- |
| `intentId` | Устойчивый идентификатор одного намерения | Обязателен; формат, срок хранения и точная проверка payload открыты |
| `employeeRef` | Ссылка на сотрудника без раскрытия профиля | Обязательна; источник и формат открыты |
| `giftCategory` | Категория подарка для проверки бизнес-правил | Обязательна; справочник открыт |
| `giftDate` | Дата события | Обязательна; календарные ограничения открыты |
| `amount.value` | Денежная величина как строка без потери точности | Обязательность и допустимый диапазон открыты |
| `amount.currency` | Валюта суммы | Обязательность и справочник открыты |
| `description` | Минимально необходимое пояснение | Необязательна; лимит, классификация и маскирование открыты |

### Учебный успешный ответ

```json
{
  "declarationId": "DECL-EXAMPLE-1042",
  "status": "SUBMITTED",
  "createdAt": "2026-08-28T10:15:00Z",
  "correlationId": "CORR-EXAMPLE-C1"
}
```

`declarationId` устойчиво обозначает созданную декларацию. `status` сообщает наблюдаемое состояние. `createdAt` фиксирует время результата; правила часового пояса и точности открыты. `correlationId` связывает диагностику одного технического прохождения и не заменяет `intentId`.

## Операция 2. Получить декларацию

| Атрибут | Решение начальной версии |
| --- | --- |
| Логическое имя | `GetGiftDeclaration` |
| Условное отображение | `GET /gift-declarations/{declarationId}` |
| Цель | Получить текущий наблюдаемый результат без изменения бизнес-состояния |
| Предусловия | Субъект распознан; право чтения конкретной декларации подтверждено |
| Параметр | `declarationId` — устойчивый идентификатор объекта |
| Успех | Идентификатор, статус и только разрешённые поля |
| Побочный эффект | Отсутствует на уровне бизнес-состояния; аудит чтения определяется классификацией данных |

Операция чтения помогает подтвердить результат после сбоя. Дополнительный поиск по `intentId`, его права и семантика — открытый вопрос, а не скрытая часть этого контракта.

## Единая модель ошибок

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Проверьте данные декларации",
  "details": [
    {"field": "giftCategory", "reason": "UNSUPPORTED_VALUE"}
  ],
  "correlationId": "CORR-EXAMPLE-C2"
}
```

| Код | Бизнес-смысл | Допустимая реакция consumer |
| --- | --- | --- |
| `VALIDATION_FAILED` | Данные отсутствуют или недопустимы | Показать исправимые поля; не повторять без изменения |
| `FORBIDDEN` | Субъект распознан, но действие не разрешено | Не повторять; показать безопасный отказ или маршрут эскалации |
| `STATE_CONFLICT` | Действие недопустимо в текущем состоянии | Обновить состояние и предложить доступный сценарий |
| `INTENT_CONFLICT` | Прежний `intentId` пришёл с иным содержимым | Не создавать объект; зафиксировать ошибку consumer и расследовать |
| `DEPENDENCY_UNAVAILABLE` | Provider не может завершить действие из-за зависимости | Следовать ограниченной политике восстановления |
| `UNKNOWN_OUTCOME` | Ответ не получен, фактический результат неизвестен | Сохранить намерение и проверить результат; не создавать новый intent вслепую |

Транспортное отображение кодов, локализация и правила раскрытия деталей открыты. Ошибки и журналы не содержат стеков, секретов, токенов и лишних персональных данных.

## Тайм-аут, повтор и восстановление

- Тайм-аут означает, что consumer не дождался ответа; он не доказывает отсутствие обработки.
- Portal сохраняет тот же `intentId` для разрешённой повторной попытки одного намерения.
- Каждая техническая попытка может иметь новый `correlationId`.
- Бесконечный немедленный retry запрещён; классы временных ошибок, число попыток и паузы должны быть согласованы эксплуатационными владельцами.
- Provider должен вернуть прежний результат того же намерения либо диагностируемый конфликт.
- После сбоя восстановление заканчивается проверкой фактического бизнес-результата, а не только получением технического ответа.
- Частичный внутренний сбой должен проявляться как определённый внешний статус либо как диагностируемый неизвестный исход; consumer не угадывает внутреннее состояние по задержке.

## Безопасность и аудит

1. Аутентификация устанавливает вызывающего субъекта; авторизация отдельно проверяет действие и область данных.
2. Сотрудник создаёт декларацию только от разрешённого имени. Офицер читает только назначенный объём.
3. Запросы и ответы содержат минимально необходимый набор. Реальные ПДн, секреты и токены не входят в примеры и не копируются в логи.
4. Значимые изменения аудируются: субъект, операция, время, бизнес-объект, исход и безопасный диагностический контекст.
5. Поведение при попытке прочитать чужой объект не должно раскрывать сам факт его существования больше, чем разрешено.
6. Механизм аутентификации, матрица прав, классификация полей и сроки аудита открыты.

## Наблюдаемость и нефункциональные требования

`correlationId` связывает события сторон. Журналы фиксируют этап и исход без секретов. Метрики различают успешный бизнес-результат, бизнес-отказ, технический сбой, неизвестный исход и задержку. Трассировка помогает восстановить путь вызова.

Нужно согласовать измеримые цели доступности, времени ответа, объёма, частоты, размеров сообщения, аудита, защиты данных и времени восстановления. Числовые пороги в исходных материалах отсутствуют и в начальной версии не выдумываются.

## Совместимость и жизненный цикл

- Владелец контракта ведёт версию и список consumers.
- Совместимость оценивается глазами выпущенных consumers и их тестов.
- Новое необязательное поле допустимо только если consumers корректно игнорируют неизвестное.
- Переименование, смена типа или бизнес-смысла используемого поля считается опасным изменением.
- Для изменения нужны уведомление, проверка, период миграции и правило вывода старого поведения.
- Номер версии не заменяет коммуникацию и не переносит consumer автоматически.

## Критерии готовности следующей версии

- владельцы подтвердили роли и source of truth;
- обе операции связаны с требованиями и state model;
- поля и ошибки согласованы с product owner, security, разработкой и QA;
- timeout/retry/recovery проверяются тестовыми сценариями;
- права, аудит и НФТ имеют подтверждённые значения;
- совместимость и миграция имеют ответственного и план.
