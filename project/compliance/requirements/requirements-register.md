# Requirements Register: Compliance

Статус: начальный черновик после урока 15.

## Поля реестра

| Поле | Смысл |
| --- | --- |
| ID | Уникальный идентификатор требования. |
| Формулировка | Что требуется от системы или процесса. |
| Тип | Functional, Nonfunctional, Constraint, Business rule. |
| Источник | Stakeholder, документ или встреча. |
| Статус | candidate, confirmed, open, deferred. |
| Приоритет | Must, Should, Could. |
| Критерий проверки | Как понять, что требование выполнено. |

## Требования-кандидаты

| ID | Формулировка | Тип | Источник | Статус | Приоритет | Критерий проверки |
| --- | --- | --- | --- | --- | --- | --- |
| REQ-CMP-001 | Сотрудник должен иметь возможность создать обращение в отдел комплаенс через портал сотрудника. | Functional | Project facts, REQ-INTRO | candidate | Must | Пользователь с ролью сотрудника создает обращение и видит его в списке своих обращений. |
| REQ-CMP-002 | Сотрудник должен видеть только свои обращения. | Constraint | Stakeholder analysis, access boundary | candidate | Must | Пользователь не получает доступ к обращениям других сотрудников через интерфейс и API. |
| REQ-CMP-003 | Комплаенс-офицер должен видеть очередь обращений, назначенных на него. | Functional | Planned interview with compliance officer | candidate | Must | Офицер открывает список назначенных обращений и видит актуальные статусы. |
| REQ-CMP-004 | Комплаенс-офицер должен иметь возможность запросить уточнение по обращению у сотрудника. | Functional | REQ-FNFR examples | candidate | Must | Офицер переводит обращение в статус уточнения, сотрудник получает запрос. |
| REQ-CMP-005 | Руководитель комплаенс должен видеть количество просроченных обращений по подразделениям. | Functional | Stakeholder register | candidate | Should | Дашборд показывает просрочки по выбранному периоду и подразделению. |
| REQ-CMP-006 | Данные дашборда руководителя должны обновляться не реже одного раза в 15 минут. | Nonfunctional | REQ-FNFR examples | candidate | Should | На дашборде отображается время последнего обновления, задержка не превышает 15 минут. |
| REQ-CMP-007 | Аутентификация пользователей должна выполняться через корпоративную SSO. | Constraint | Project facts | candidate | Must | Пользователь входит через SSO, локальная парольная учетная запись не используется. |
| REQ-CMP-008 | Действия с изменением статуса обращения должны попадать в журнал аудита. | Nonfunctional | Security stakeholder hypothesis | candidate | Must | Для каждого изменения статуса есть запись: кто, когда, что изменил. |

## Требования, требующие уточнения

- Какие статусы обращения входят в первую версию?
- Какой срок ответа считается нормативным для обычного обращения?
- Кто утверждает продление срока обработки?
- Какие поля регистрации подарка обязательны всегда, а какие зависят от суммы или категории?

## Добавлено после урока 21: state model

| ID | Формулировка | Тип | Источник | Статус | Приоритет | Критерий проверки |
| --- | --- | --- | --- | --- | --- | --- |
| REQ-CMP-014 | Система должна хранить статус обращения как одно из допустимых значений жизненного цикла: `Draft`, `Submitted`, `In review`, `Clarification requested`, `Answered`, `Closed`, `Cancelled`. | Business rule | State model: жизненный цикл обращения | candidate | Must | Нельзя сохранить обращение со статусом вне утвержденного перечня. |

| REQ-CMP-016 | После перехода обращения в `Submitted` сотрудник не должен редактировать исходный текст обращения, кроме ответа на запрос уточнения. | Functional / access rule | State model: ограничения состояний | candidate | Must | В статусах после отправки исходные поля обращения недоступны для редактирования сотрудником. |

| REQ-CMP-018 | Система должна сохранять дату, время, инициатора и исходный/целевой статус для каждого значимого перехода обращения. | Nonfunctional / audit | State model: audit actions | candidate | Must | В журнале аудита есть запись по каждому изменению статуса с инициатором и парой статусов. |
