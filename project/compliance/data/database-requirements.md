# Требования к данным и базе данных Compliance

Статус: начальная каноническая версия после урока 43 `DB-INTRO`  
Версия: 0.1  
Владелец документа: системный аналитик Compliance Platform  
Дата начала: 2026-08-28

## 1. Назначение

Документ фиксирует требования к хранению и управлению данными внутренней Compliance-системы до проектирования логической и физической модели. Он служит входом для модели данных, словаря данных, API, разработки, тестирования, информационной безопасности и эксплуатации.

Термин «требования к БД» здесь означает требования к данным и поведению хранилища в составе системы. Документ не выбирает конкретную СУБД и не утверждает структуру таблиц.

## 2. Границы версии 0.1

В область входят данные об обращениях, подарках, декларациях, обработке комплаенс-офицерами и отчётности руководителя на уровне требований. Учитываются идентификация объектов, состояния, история, качество, доступ, аудит, жизненный цикл и восстановление.

Вне области этой версии:

- логическая ER-модель и физическая схема;
- таблицы, столбцы, типы данных, первичные и внешние ключи;
- SQL, индексы, транзакционные настройки и конфигурация СУБД;
- подтверждение конкретного продукта СУБД;
- числовые НФТ без источника и владельца.

## 3. Подтверждённый контекст

1. Compliance — внутренняя корпоративная система для сотрудников, комплаенс-офицеров и руководителя комплаенс.
2. Система поддерживает обращения, подарки, декларации, их обработку и отчётность.
3. Сотрудник работает через портал и не должен получать доступ к данным других сотрудников вне разрешённого сценария.
4. Комплаенс-офицер обрабатывает назначенные объекты; руководитель использует сводную аналитику.
5. Значимые изменения состояния должны быть проверяемыми и аудируемыми.
6. Точный состав полей, сроки хранения, объёмы, числовые НФТ и production-технология не подтверждены.

## 4. Принципы

### DBR-PR-001. Бизнес-смысл прежде реализации

Каждый сохраняемый набор данных должен быть связан с подтверждённым бизнес-объектом, сценарием или обязательством. Поле макета или техническое удобство само по себе не является основанием хранить данные.

### DBR-PR-002. Явное владение

Для каждой ключевой группы данных должны быть определены владелец смысла и источник истины. Локальная копия не становится источником истины автоматически.

### DBR-PR-003. Минимизация

Система хранит, передаёт, журналирует и копирует только данные, необходимые подтверждённым сценариям, контролям и регламентам.

### DBR-PR-004. Проверяемость

Требование считается готовым к реализации, когда имеет наблюдаемый критерий, источник, владельца и связь со сценарием или артефактом.

## 5. Требования-кандидаты

Все пункты раздела имеют статус `candidate` и требуют подтверждения соответствующими владельцами.

| ID | Требование-кандидат | Критерий проверки | Основной владелец подтверждения |
| --- | --- | --- | --- |
| DBR-ID-001 | Каждый операционный бизнес-объект должен иметь устойчивый идентификатор, однозначно различающий экземпляры в пределах согласованной области. | Повторное чтение и связанные операции обращаются к тому же объекту; коллизия выявляется. | Архитектор / data owner |
| DBR-ID-002 | Связь объекта с сотрудником и другими владельцами должна использовать подтверждённые идентификаторы источников истины. | Объект нельзя ошибочно связать с другим сотрудником при повторной синхронизации. | Data owner / владелец HR-источника |
| DBR-STATE-001 | Для объектов с жизненным циклом должно храниться текущее состояние из согласованного набора. | Недопустимое состояние отклоняется; UI и API получают согласованный смысл. | Product owner / Compliance SME |
| DBR-STATE-002 | Изменение состояния должно соответствовать разрешённому переходу, роли и предусловиям. | Запрещённый переход не изменяет бизнес-состояние и даёт диагностируемый результат. | Product owner / системный аналитик |
| DBR-HIST-001 | Значимые изменения должны оставлять историю, достаточную для объяснения перехода: объект, прежнее и новое состояние или действие, субъект, время и исход. | По истории можно восстановить последовательность значимых действий без чтения небезопасных технических логов. | Внутренний аудит / security |
| DBR-INT-001 | Обязательность и допустимость значений должны зависеть от бизнес-состояния и сценария, а не только от наличия поля на экране. | Неполный черновик и отправленный объект проверяются по разным подтверждённым правилам. | Product owner / QA |
| DBR-INT-002 | Система должна предотвращать необъяснимые дубли при повторной отправке одного бизнес-намерения. | Повтор распознаётся и не создаёт второй эффект либо возвращает определённый конфликт. | Владелец сервиса / архитектор |
| DBR-ACCESS-001 | Доступ к данным должен проверять отдельно субъект, действие и область объектов. | Сотрудник не читает чужой объект; офицер получает только разрешённый объём. | Security / product owner |
| DBR-ACCESS-002 | Технические доступы приложений, администраторов, отчётности и интеграций должны предоставляться по принципу минимальных полномочий. | Для каждой учётной записи есть владелец, назначение и ограниченный набор операций. | Security / эксплуатация |
| DBR-MIN-001 | Пользовательские ответы, API, выгрузки, логи, тестовые среды и резервные копии не должны содержать избыточные чувствительные данные. | Для каждой копии определены назначение, состав, защита и срок жизни. | Security / data owner |
| DBR-AUD-001 | Доступ и значимые изменения должны аудироваться в подтверждённом объёме без создания незащищённой полной копии объекта. | Аудит связывает субъекта, действие, время, объект и исход; секреты и лишние данные отсутствуют. | Внутренний аудит / security |
| DBR-LIFE-001 | Для каждой группы данных должны быть определены срок хранения и действие по его окончании: сохранение, архивирование, обезличивание или удаление. | Политика имеет нормативное или бизнес-основание, владельца и проверяемое исполнение. | Юридическая служба / аудит |
| DBR-QUAL-001 | Для критичных атрибутов должны быть определены бизнес-смысл, источник, формат, единицы, обязательность, допустимые значения и правило исправления. | Словарь данных позволяет разработке и QA одинаково интерпретировать значение. | Data owner / системный аналитик |
| DBR-SYNC-001 | Для копируемых данных должны быть определены источник истины, частота/событие обновления, допустимая задержка и обработка расхождений. | Расхождение обнаруживается, имеет владельца и согласованный маршрут исправления. | Владельцы обеих систем |
| DBR-VOL-001 | До выбора физической реализации должны быть подтверждены текущий объём, рост, пиковая частота операций и характер основных выборок. | Архитектурное решение ссылается на измеримые исходные значения и прогноз. | Product owner / архитектор |
| DBR-PERF-001 | Для критичных сценариев должны быть определены измеримые цели времени ответа и доступности с условиями измерения. | НФТ имеет число, период, нагрузочный профиль, метод измерения и владельца. | Product owner / эксплуатация |
| DBR-REC-001 | Должны быть определены допустимая потеря данных, целевое время восстановления и критерий подтверждения фактического бизнес-состояния после сбоя. | Процедура восстановления проверена; результат сверяется на уровне бизнес-объектов. | Бизнес-владелец / эксплуатация |
| DBR-ENV-001 | Использование production-данных в непроизводственных средах допускается только по подтверждённому правилу защиты, минимизации или обезличивания. | Тестовая среда не содержит неразрешённых production-данных; исключения задокументированы. | Security / QA lead |

## 9. Критерии готовности к следующей детализации

Артефакт готов к построению первой логической модели, когда:

- подтверждены владельцы ключевых объектов и источники истины;
- согласованы границы хотя бы одного приоритетного сценария;
- известны обязательные данные и правила состояний для этого сценария;
- определены роли и область доступа;
- открытые вопросы имеют владельцев и план закрытия;
- модель данных можно трассировать к требованиям и поведению системы;
- физические решения не маскируют неподтверждённые бизнес-правила.

## 10. Ограничение по источникам

На момент версии 0.1 каталог зарегистрированных авторских материалов по теме пуст, а внешнее исследование запрещено паспортом урока. Поэтому документ не утверждает конкретные production-поля, сроки, числа, СУБД или физическую схему. Они остаются кандидатами и открытыми вопросами до подтверждения источниками и владельцами.
