# Идемпотентное списание: платёжный запрос к REST API

Задача: `int-idempotency`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Спроектировать операцию списания денег так, чтобы повторная отправка запроса не списала деньги дважды.

## Контекст

- Мобильное приложение отправляет в платёжный сервис запрос `POST /v1/payments` — списание с карты клиента в пользу магазина. Сеть мобильная: запросы теряются, приложение повторяет отправку, пользователь может нажать кнопку дважды.
- Со стороны платёжного сервиса есть банк-эквайер, который тоже отвечает с задержкой и иногда «зависает»: деньги уже списаны, а ответа мы не получили.
- Инциденты двойных списаний — это деньги клиентов, жалобы, чарджбэки и штрафы регулятора. Задача: сделать операцию идемпотентной на всех участках цепочки.

## Цель

Описать контракт и поведение операции списания, при котором любой повтор запроса безопасен, а состояние платежа всегда объяснимо.

## Исходные данные

- Сумма, валюта, идентификатор карты (токен), идентификатор заказа, идентификатор клиента.
- Клиентское мобильное приложение, сервер платёжного сервиса, внешний эквайринг.
- Текущий контракт: `POST /v1/payments` без каких-либо ключей идемпотентности.
- Требование бизнеса: пользователь всегда видит однозначный результат — «оплачено», «не оплачено» или «платёж обрабатывается».

## Ограничения

- Эквайринг менять нельзя, он не идемпотентен по своим внутренним причинам.
- Срок жизни ключа идемпотентности ограничен: хранить вечно нельзя.
- Ответ клиенту — в пределах 3 секунд, дальше только асинхронные уведомления.

## Ожидаемые результаты

- Контракт запроса и ответа: поля, коды HTTP, ключ идемпотентности, кто его генерирует и как долго он живёт.
- Модель состояний платежа и переходы между ними.
- Поведение при дублях запроса: что возвращаем, если платёж уже создан, уже успешен, уже отклонён или ещё в работе.
- Обработка «зависшего» эквайринга: как узнаём истинный результат и что показываем пользователю.
- Граничные случаи: сумма изменилась при том же ключе, ключ переиспользован для другого заказа, истёк срок хранения ключа.
- Что нужно для эксплуатации: логи, метрики, поддержка разборов «клиент говорит, что списали дважды».

## Вопрос задания

«Расскажите, как вы спроектируете идемпотентный платёжный запрос. Что будет, если клиент отправит его дважды, а эквайринг на первый запрос не ответил?»
