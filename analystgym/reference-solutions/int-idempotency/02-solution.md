# Идемпотентное списание: платёжный запрос к REST API

Задача: `int-idempotency`. Версия БД: **0**. Статус: **published**.

**Статус: условный черновик эталона, до ответов на вопросы.** Предложенные варианты и параметры не добавляют фактов к условию.

## Решение

1. При POST использовать стабильный Idempotency-Key в области клиента/магазина и операции. Атомарно сохранять ключ, канонические значимые поля, payment_id и состояние. Конфликт тела под тем же ключом отклонять; конкурентные одинаковые запросы получают одну локальную операцию.

2. Отделить создан, отправка начата, обрабатывается/исход неизвестен, успешен, подтверждённо отклонён. Повтор возвращает ту же операцию и её актуальный статус; клиент получает результат или processing в пределах 3 секунд.

3. Зафиксировать намерение внешнего вызова и защитить локальную выдачу работы от дублей. После падения в промежутке «вызов мог уйти, ответ не сохранён» не отправлять неидемпотентное списание повторно автоматически. Разрешать исход через status/webhook/сверку с проверкой подлинности и корреляции.

4. Если механизма выяснения исхода нет, держать операцию на ручной сверке и явно зафиксировать ограничение автоматизации. Доставка задания хотя бы один раз сама по себе не даёт единственности списания во внешней системе.

5. TTL транспорта согласовать с окнами повторов, но после его истечения не считать старую бизнес-операцию новой автоматически: хранить долговечную связь с заказом/платежом по согласованной политике. Новая законная попытка после отказа получает отдельную идентичность.

## Как проверить качество результата

Два конкурентных POST создают одну локальную операцию; изменение значимых полей вызывает конфликт. Проверить падение до/после отправки, повтор webhook, истёкший ключ и новую допустимую попытку. Неизвестный внешний исход не переименовывается в failed по одному таймауту.

## Диагностика инцидентов в проектируемой системе

payment_id, order_id, псевдонимизированный контекст клиента, защищённый отпечаток ключа, fingerprint тела, acquire_reference, переходы состояния, источник подтверждения и reconciliation_id; без токена карты, секретов и полного тела.

Это требования к решению учебного кейса. Изменения в работающий сервис этим пакетом не внесены.
