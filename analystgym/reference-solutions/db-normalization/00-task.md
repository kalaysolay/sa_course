# Таблица заявок «как в Excel» → нормальная схема

Задача: `db-normalization`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Одна широкая таблица на 60 колонок хранит заявки. Дубли, расхождения, невозможность отчётности. Нужна нормализация.

## Контекст

- Сервисный центр принимает заявки на ремонт. Всё живёт в таблице `requests` на 60 колонок: данные клиента (ФИО, телефон, адрес), данные устройства (марка, модель, серийный номер), данные заявки (дата, статус, исполнитель, стоимость), текстовые поля («описание неисправности», «что сделано», «комментарий руководителя»), а также колонки вида «услуга1», «услуга2», «услуга3» с ценами.
- Проблемы: один клиент с тремя заявками заведён трижды с разными написаниями телефона; историю статусов не восстановить; отчёт по выручке в разрезе услуг считается вручную, потому что услуг может быть больше трёх; исполнители жалуются, что «всё в одну кучу».
- Разработка готова переделать схему, но просит обоснование и план переноса данных — система работает, заявки терять нельзя.

## Цель

Спроектировать нормализованную схему, объяснить выбор, описать план переноса данных и что изменится для пользователей и отчётности.

## Исходные данные

- Текущая таблица: 60 колонок, 1,2 млн строк, рост 8 тысяч заявок в месяц.
- Колонки «услуга1..3» заполнены на 65%, у 12% заявок услуг больше трёх — их дописывают в текстовый комментарий.
- Телефон клиента хранится в свободном формате: «89161234567», «+7 (916) 123-45-67», «916-123-45-67».
- Статусы заявки меняются по 5–8 раз, история нигде не сохраняется.
- Пользователи: приёмщик, мастер, руководитель отдела, бухгалтерия.

## Ограничения

- Система работает 24/7, простой не более 30 минут.
- Исторические данные должны остаться доступны: старые заявки нужны для гарантийных обязательств.
- Приёмщики не должны учиться работать заново: экран создания заявки остаётся таким же по скорости.

## Ожидаемые результаты

- Целевая схема: сущности, атрибуты, ключи, связи, обоснование нормальных форм (какие НФ достигаются и почему дальше не идём).
- Решение для услуг заявки (вместо «услуга1..3») и для истории статусов.
- Справочники: что выносим в них, как поддерживаем.
- План переноса данных: очистка, дубли клиентов, маппинг, проверка, этапы, откат.
- Влияние на интерфейсы и отчётность: что станет возможным, что сломается.
- Осознанная денормализация, если она нужна, с обоснованием.

## Вопрос задания

«У вас таблица на 60 колонок. Нормализуйте. До какой НФ и почему не дальше? Как перенесёте данные без простоя?»
