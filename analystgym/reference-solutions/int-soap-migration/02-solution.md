# Перевод интеграции с SOAP на REST без остановки потока

Задача: `int-soap-migration`. Версия БД: **0**. Статус: **published**.

**Статус: условный черновик эталона, до ответов на вопросы.** Предложенные варианты и параметры не добавляют фактов к условию.

## Решение

1. Составить инвентаризацию операций и потребителей. По реальным спецификациям заполнить матрицу: SOAP-операция/поле → REST-ресурс/действие, типы, обязательность, семантика, ошибка, подпись, источник отсутствующих значений и владелец согласования.

2. Ввести внутреннюю каноническую заявку и адаптеры каналов. Сохранять исходные учётные поля локально и обогащать входящий результат только при наличии надёжного источника. Если поле рождается исключительно у партнёра и исчезает, зафиксировать блокер процесса; не подставлять фиктивное значение.

3. Моделировать accepted/processing/completed/failed для REST, сохранять внешний ID до ожидания webhook, проверять события, дедуплицировать и иметь путь сверки зависших заявок.

4. Начать с контрактных тестов и воспроизведения обезличенных примеров. В проде сравнивать безопасные чтения или результаты единственного пишущего канала. Переключать по группе операций/клиентов с закреплением канала за уже созданной заявкой.

5. До отключения SOAP держать проверенный возврат маршрута новых заявок, завершать начатые по их каналу. Критерии расширения: сверка бизнес-результатов, приемлемые задержки и отсутствие необъяснённых потерь. После дедлайна возврат на SOAP больше не является рабочим планом.

## Как проверить качество результата

Каждая реально используемая операция имеет согласованное соответствие либо явно решённый пробел; входящие и исходящие заявки сверяются. Отказы webhook и смена маршрута не теряют начатые операции; сценарий отката проверен до срока отключения.

## Диагностика инцидентов в проектируемой системе

canonical_request_id, SOAP/REST channel, external_id, версии контракта/маппинга, этап, статус подписи, webhook_event_id, результат сверки и причина смены канала. Не включать исходные клиентские XML/JSON в обычный лог.

Это требования к решению учебного кейса. Изменения в работающий сервис этим пакетом не внесены.
