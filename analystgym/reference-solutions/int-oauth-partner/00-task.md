# Доступ партнёра к нашему API: OAuth 2.0, лимиты и аудит

Задача: `int-oauth-partner`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Три внешних партнёра получают доступ к нашему REST API. Нужна схема авторизации, права, лимиты и аудит.

## Контекст

- Вы аналитик платформы. Продукт — B2B-сервис, у нас есть публичный REST API. Три партнёра хотят интеграцию: агрегатор (читает данные о заказах своих клиентов), бухгалтерский сервис (читает и создаёт документы), крупный корпоративный клиент (управляет своими сотрудниками и настройками).
- Сейчас партнёрам выдают «общий токен в конфиге», который не истекает. Безопасность требует закрыть эту практику: нужны отдельные учётные данные на партнёра, ограниченные права, возможность отозвать доступ за минуты и полный аудит обращений.
- Есть требования регулятора по защите персональных данных: партнёры не должны получать больше данных, чем нужно для их сценария.

## Цель

Спроектировать модель доступа партнёров к API: грант-тип OAuth 2.0, скоупы и права, жизненный цикл учётных данных, лимиты, аудит и процесс подключения/отключения партнёра.

## Исходные данные

- Три разных профиля доступа (чтение, чтение+запись, управление настройками).
- У каждого партнёра несколько окружений (тест и прод) и возможность ротации секретов.
- Ожидаемая нагрузка: агрегатор — 50 rps, бухгалтерия — 5 rps, корпоративный клиент — 1 rps с пиками в отчётные периоды.
- Данные в API включают персональные данные клиентов и сотрудников.

## Ограничения

- Нельзя требовать от партнёров хранить секреты в браузере или мобильном клиенте — интеграции сервер-сервер.
- Отзыв доступа должен занимать минуты, не дни.
- Мы не можем хранить пароли партнёров в открытом виде и не должны видеть их секреты после выдачи.

## Ожидаемые результаты

- Выбор грант-типа OAuth 2.0 с обоснованием (почему не другой), описание потока получения и обновления токена.
- Модель скоупов и прав: гранулярность по ресурсам и операциям, как скоупы связываются с учёткой партнёра.
- Жизненный цикл секретов: выдача, хранение, ротация, отзыв, срок жизни токенов.
- Лимиты (rate limiting): по какому признаку, какие значения, что возвращаем при превышении, деградация.
- Аудит и безопасность: что логируем, как расследуем инцидент, защита от утечки токена, передача ПДн.
- Операционный процесс: подключение партнёра, смена прав, отзыв доступа, что делает поддержка.
- Ошибки и отказы: какие коды и сообщения видит партнёр, как он понимает, что превысил лимит или потерял права.

### Sequence: получение токена

Тип: plantuml.

```text
@startuml
autonumber
participant "Сервис партнёра" as P
participant "Auth Server" as AUTH
participant "API Gateway" as GW
participant "Ресурс-сервис" as API
database "Учётные данные" as DB

P -> AUTH: POST /oauth/token\ngrant_type=?
AUTH -> DB: проверить client_id / secret
DB --> AUTH: ?
AUTH --> P: access_token + ?
P -> GW: GET /v1/orders\nAuthorization: Bearer ?
GW -> GW: проверить токен и скоупы
GW -> API: запрос
API --> GW: данные
GW --> P: 200 / 403 / 429 ?
@enduml

```
