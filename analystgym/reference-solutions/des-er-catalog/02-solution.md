# Модель данных каталога товаров: от Excel-таблицы к схеме

Задача: `des-er-catalog`. Версия БД: **0**. Статус: **published**.

**Статус: условный черновик эталона, до ответов на вопросы.** Предложенные варианты и параметры не добавляют фактов к условию.

## Решение

1. Предложить PRODUCT(id, name, description, brand_id), VARIANT(id, product_id, sku unique), WAREHOUSE(id), CATEGORY(id, parent_id) и связи категорий по согласованной кардинальности. Выделить различие модели товара и продаваемой позиции.

2. Для VARIANT–WAREHOUSE хранить отдельную запись с составным уникальным ключом и согласованными видами количества. Цену связывать с вариантом и складом; валюту и период действия добавлять, если они подтверждены. Использовать точные числовые типы и ограничения согласованного диапазона.

3. Сравнить типизированную таблицу характеристик/значений и JSON с валидируемой схемой категории. Не дублировать размер одновременно в нескольких источниках истины. Выбрать вариант по требованиям фильтрации, изменения схемы и обязательности.

4. Развести текущую цену и историю либо использовать интервальную модель с запретом пересечения действующих периодов для одной комбинации измерений. В одной транзакции фиксировать изменение и автора/основание. Для удаления использовать архивирование там, где нужны ссылки из истории.

## Как проверить качество результата

Два варианта не имеют одного SKU; изменение описания товара не требует правки каждой складской записи. Можно получить текущую цену пары и объяснить её изменение. Проверить отсутствующий складской остаток, конкурирующее изменение цены и архивирование связанного объекта.

## Диагностика инцидентов в проектируемой системе

product_id, variant_id, warehouse_id, price_change_id, автор, основание, старое/новое значение цены в защищённом аудите, effective_at, версия правила; импорт — batch_id, результат валидации и конфликт SKU.

Это требования к решению учебного кейса. Изменения в работающий сервис этим пакетом не внесены.
