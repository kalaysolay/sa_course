# Миграция 200 млн строк без простоя: план и риски

Задача: `db-migration`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Историческую таблицу транзакций надо разбить на новую схему и перенести в другой кластер. Сервис работает 24/7.

## Контекст

- Финтех-компания. Таблица `transactions` — 200 млн строк, 340 ГБ, растёт на 1,5 млн строк в сутки. Она живёт в одном кластере с операционной нагрузкой, запросы истории начали мешать оформлению платежей.
- Решено: перейти на новую схему (другая структура полей, разделение на таблицу операций и таблицу проводок) и перенести данные в отдельный кластер, оптимизированный под чтение истории.
- Простой сервиса недопустим: платежи идут круглосуточно, пик — будни 10:00–14:00. Окно на миграцию — 3 месяца, команда 2 разработчика и аналитик.

## Цель

Составить план миграции: целевая схема и маппинг, стратегия переноса (батчи/CDC), обеспечение согласованности, валидация, переключение, откат, эксплуатация во время миграции.

## Исходные данные

- Новая схема: `operations` (операция: клиент, сумма, статус, тип) + `postings` (проводки по операции: счёт, сумма, направление) — нормализация «одна операция → много проводок».
- В старой таблице проводки лежат в двух колонках `debit_account`/`credit_account`, а для многосторонних операций — в JSON-поле `extra_postings` (заполнено у 8% строк).
- Часть исторических данных неконсистентна: 0,3% строк имеют нулевую сумму, 120 тысяч строк — статус, которого нет в новом справочнике.
- Требование: после миграции история должна читаться с той же производительностью или лучше, а данные — совпадать с источником построчно.

## Ограничения

- Простой недопустим. Нагрузка на исходный кластер во время миграции не должна превышать +15% по CPU/IO.
- Окно 3 месяца, 2 разработчика.
- Финансовые данные: расхождение даже в одну строку недопустимо, требуется аудиторский след миграции.

## Ожидаемые результаты

- Маппинг полей и трансформации, включая разбор JSON-проводок и обработку неконсистентных данных.
- Стратегия переноса: исторический батч + инкремент (CDC или двойная запись), порядок, управление нагрузкой на источник.
- Обеспечение согласованности: как не потерять и не задвоить строки при работающем сервисе, точка пересечения батча и инкремента.
- Валидация: сверки (объёмы, суммы, контрольные выборки), критерии приёмки каждого этапа.
- Переключение чтения и записи: этапы, feature flags, канарейка, точка невозврата.
- План отката на каждом этапе и критерии его запуска.
- Эксплуатация: мониторинг прогресса, оценка сроков, действия при деградации источника, коммуникация с командой поддержки.
- Риски и как их снижаем.

### Этапы и потоки

Тип: plantuml.

```text
@startuml
database "Источник: transactions\n200M строк" as SRC
node "Мигратор (батчи)" as MIG
queue "CDC / двойная запись" as CDC
database "Цель: operations + postings" as DST
rectangle "Сервис платежей" as APP

SRC -> MIG : исторический перенос
SRC -> CDC : изменения онлайн
CDC -> DST : инкремент
MIG -> DST : батчи
APP -> SRC : запись (пока)
APP -> DST : чтение (канарейка)
@enduml

```
