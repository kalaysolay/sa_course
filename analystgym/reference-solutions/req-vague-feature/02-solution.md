# «Хотим как у конкурентов»: из идеи в требования

Задача: `req-vague-feature`. Версия БД: **0**. Статус: **published**.

**Статус: условный черновик эталона, до ответов на вопросы.** Предложенные варианты и параметры не добавляют фактов к условию.

## Решение

1. В первые дни провести интервью с маркетингом, продуктом, аналитикой, разработкой и владельцем данных. Вести реестр вопросов с владельцем, датой и последствием отсутствия ответа; цель и метрики утвердить до обещания реализации.

2. Сформулировать проверяемую гипотезу с пустыми до согласования baseline/целевым эффектом, аудиторией и сроком. Определить ограничения данных и процесса поддержки.

3. Как кандидат MVP предложить простую подборку по доступным категориям/просмотрам с контролируемыми правилами и fallback на редакционную подборку. ML, сложные профили и копирование неизвестного X не включать без обоснования.

4. Пример историй: вернувшийся пользователь видит согласованное число доступных курсов из разрешённых категорий; новый получает редакционную подборку; отказавшийся от персонализации получает общий вариант; при пустом результате/отказе зависимости страница показывает fallback. Число карточек и задержки — предлагаемые параметры, не факты задачи. Для каждой истории задать дано/когда/тогда, исключение купленных/недоступных курсов — только после согласования правила.

5. К концу двух недель передать цели, границы первой версии, 3–5 историй, НФТ, макет сценария, план эксперимента и открытые решения. Назначить владельца правил, событий измерения и наблюдения после запуска.

## Как проверить качество результата

Каждая история проверяема, альтернативные сценарии описаны, неизвестные имеют владельцев и срок. Гипотеза связана с измеримой целью, scope укладывается в подтверждённую ёмкость, план эксперимента не обещает статистическую определённость без расчёта.

## Диагностика инцидентов в проектируемой системе

discovery_question_id, decision_id, requirements_version, rule_version, experiment_id, recommendation_request_id, fallback_reason и агрегированные метрики; не писать историю просмотров и профили в обычный лог.

Это требования к решению учебного кейса. Изменения в работающий сервис этим пакетом не внесены.
