# Событийная интеграция заказа: Kafka, гарантии и согласованность

Задача: `int-kafka-events`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Синхронную цепочку «заказ → оплата → склад → доставка» надо перевести на событийную модель. Нужна схема, гарантии и план разбора сбоев.

## Контекст

- Онлайн-ритейлер. Сейчас создание заказа — один большой синхронный вызов: сервис заказов по очереди вызывает оплату, склад (резервирование товара) и доставку (слот и стоимость). Любая из систем отвечает медленно — заказ не создаётся, пользователь видит ошибку, склад при этом может остаться с зарезервированным товаром.
- Компания переходит на событийную архитектуру: сервис заказов публикует события в Kafka, остальные системы подписываются. Есть требование бизнеса: пользователь должен видеть статус заказа в реальном времени, а отмена заказа — работать даже если товар уже резервируется.
- Исторические данные: 2,5 млн заказов в сутки в пик распродаж. Команда эксплуатации требует, чтобы любой сбой разбирался по логам без участия разработчиков.

## Цель

Спроектировать событийную схему потока заказа: состав событий, гарантии доставки и порядка, обработка отказов и согласованность между сервисами, наблюдаемость.

## Исходные данные

- Участники: Сервис заказов, Оплата, Склад, Доставка, Уведомления, Аналитика.
- Бизнес-правила: товар резервируется только после успешной оплаты; доставка считается только при наличии резерва; отмена возможна до передачи в доставку.
- Требование: не более 0,01% «потерянных» заказов, расхождения между сервисами должны выявляться автоматически.
- Технология обмена — Kafka (топики, партиции, consumer groups). Другие брокеры не рассматриваем.

## Ограничения

- Полностью синхронный UX при оформлении сохранить нельзя — но пользователь не должен видеть «подвисший» заказ дольше 10 секунд без объяснения.
- Оплата — внешний платёжный провайдер, его поведение не детерминировано.
- Команда склада не готова менять свою схему БД в ближайшие полгода.

## Ожидаемые результаты

- Перечень событий и топиков: имя, состав полезной нагрузки, кто публикует, кто потребляет.
- Схема потока (диаграмма) с основным и альтернативными сценариями: оплата не прошла, товара нет на складе, доставка не смогла рассчитать слот, пользователь отменил заказ.
- Механизм согласованности: сага (оркестрация или хореография), компенсирующие действия, кто за что отвечает.
- Гарантии: at-least-once / exactly-once, дубли сообщений, порядок событий, идемпотентность потребителей.
- Партиционирование и ключи: как обеспечить порядок для одного заказа и параллельность между заказами.
- Наблюдаемость и разбор сбоев: correlation id, состояние саги, дедлайн-очереди, метрики, алерты, экран разбора для поддержки.
- Что меняется для пользователя: статусы заказа, уведомления, поведение при зависшем сценарии.

## Вопрос задания

«Спроектируйте событийный поток оформления заказа в Kafka. Как вы обеспечите согласованность, если склад зарезервировал товар, а оплата не прошла? И как вы будете разбирать инциденты?»

### Sequence: основной поток

Тип: plantuml.

```text
@startuml
autonumber
participant "Сервис заказов" as ORD
queue "Kafka" as K
participant "Оплата" as PAY
participant "Склад" as WH
participant "Доставка" as DLV
participant "Уведомления" as NOTIF

ORD -> K: OrderCreated
K -> PAY: OrderCreated
PAY -> K: PaymentSucceeded
K -> WH: PaymentSucceeded
WH -> K: StockReserved
K -> DLV: StockReserved
DLV -> K: DeliveryScheduled
K -> NOTIF: DeliveryScheduled
NOTIF -> ORD: ?
@enduml

```

Тип: mermaid.

```text
flowchart TD

  C -->|успех| D[Расчёт доставки]

  D -->|успех| E[Заказ подтверждён]
```
