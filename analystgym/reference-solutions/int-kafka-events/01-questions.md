# Событийная интеграция заказа: Kafka, гарантии и согласованность

Задача: `int-kafka-events`. Версия БД: **0**. Статус: **published**.

## Вывод по полноте

Нужно устранить противоречие: правило разрешает резерв только после успешной оплаты, а interview спрашивает о резерве при неуспешной оплате. Также нельзя считать среднесуточную нагрузку пиковой.

## Открытые вопросы

Для каждого вопроса нужны ответ, источник и решение: дополнить условие / оставить частью задания / разрешить явное допущение. Ответы пока не получены.

### int-kafka-events-Q01 · P0 · Противоречие

**Вопрос пользователя:** Резерв до успешной оплаты запрещён. Случай «резерв есть, оплата не прошла» — историческая аномалия, поздняя отмена/сторно оплаты или всё же разрешённая параллельная схема?

**Зачем нужен ответ:** Меняет нормальный порядок саги и набор компенсаций; оба прочтения нельзя скрыто оценивать одним эталоном.

**Предлагаемый адресат:** Владелец заказов. **Статус:** открыт.

### int-kafka-events-Q02 · P0 · Данные

**Вопрос пользователя:** Какие операции складского API доступны без изменения БД: резерв по order_id, проверка результата, отмена, срок резерва, идемпотентность?

**Зачем нужен ответ:** Нельзя навязать outbox в БД склада при запрете менять схему; нужен реализуемый адаптер.
