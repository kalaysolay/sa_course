# Витрина выручки: данные, качество и SLA отчётности

Задача: `db-dwh-metrics`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Финансисты и коммерческий директор считают выручку по-разному и получают разные цифры. Нужна единая витрина.

## Контекст

- Компания продаёт подписки (B2B SaaS) и разовые услуги. Выручку сейчас считают в трёх местах: бухгалтерия — в учётной системе по закрытым актам, коммерческий отдел — в CRM по оплаченным счетам, аналитик — в Excel по выгрузке из биллинга. Цифры расходятся на 4–7%, и каждый месяц совет директоров начинается со спора «чья цифра правильная».
- Задача: построить единую витрину данных по выручке с понятными правилами расчёта, качеством данных и SLA обновления.
- Есть требования: признание выручки по методу начисления (не по оплате), разбивка по продуктам и сегментам клиентов, ретроспектива 3 года, обновления ежедневно к 9:00.

## Цель

Спроектировать витрину: источники, модель данных, бизнес-правила расчёта метрик, качество данных, SLA и процесс согласования определений.

## Исходные данные

- Источники: биллинг (подписки и платежи), CRM (сделки и клиенты), учётная система (акты и закрывающие документы), сервис поддержки (возвраты и претензии).
- Расхождения: CRM считает выручкой оплаченный счёт, бухгалтерия — подписанный акт, биллинг — начисление по графику подписки.
- Есть возвраты, скидки, многоэтапные сделки (пилот → продление), апгрейды подписки в середине периода, продажи через партнёров.
- Потребители: CFO, коммерческий директор, совет директоров, продуктовые команды, финансисты для отчётности.

## Ограничения

- Бухгалтерская отчётность остаётся источником истины для регулятора: витрина не подменяет её, а объясняет различия.
- Источники не могут быть изменены быстро: CRM заполняют менеджеры как хотят.
- Отчёт к 9:00 каждый день, включая дни закрытия месяца.

## Ожидаемые результаты

- Реестр метрик выручки с едиными определениями (что такое выручка, MRR/ARR, признанная выручка, отток) и владельцами определений.
- Модель данных витрины: слои (источники → детальная → агрегаты), ключевые таблицы и измерения.
- Правила расчёта для сложных случаев: апгрейд в середине месяца, возврат, скидка, партнёрская продажа, многолетний контракт.
- Качество данных: проверки, классификация ошибок, что делать с «грязными» данными в отчёте.
- SLA: время готовности, допустимая задержка, действия при сбое, кто уведомляется.
- Процесс: как согласуются новые метрики, как решается спор о цифрах, как меняются определения во времени.
- Как объяснять расхождение с бухгалтерской отчётностью (а не прятать его).
