# Контракт API для мобильного приложения: версии, пагинация, ошибки

Задача: `req-api-contract`. Версия БД: **0**. Статус: **published**.

Снимок: `../snapshot.json`, поле `tasks`, поиск по ID. Это исходные данные, а не предложенные дополнения.

## Кратко

Мобильное приложение получает данные «как получится». Нужен согласованный контракт, который переживёт обновления приложения.

## Контекст

- У продукта есть веб и мобильное приложение (iOS/Android). Бэкенд отдаёт данные через набор REST-эндпоинтов, которые исторически выросли из внутреннего API. Мобильная команда жалуется: при изменении полей приложение падает, пагинации нет (список из 5 000 элементов приходит целиком), ошибки возвращаются в разном формате, а старые версии приложения в маркете живут годами.
- Сейчас 22% пользователей на версиях приложения старше 6 месяцев. Любое ломающее изменение API = тысячи неработающих установок и шквал отзывов.
- Нужно спроектировать контракт для нового раздела «Мои операции» и зафиксировать правила, по которым API будет развиваться дальше.

## Цель

Описать контракт эндпоинтов раздела (методы, поля, типы, обязательность, коды ответов), правила версионирования и обратной совместимости, пагинацию, обработку ошибок и нефункциональные требования.

## Исходные данные

- Раздел «Мои операции»: список операций пользователя (до 5 000 за год), фильтр по периоду и типу, карточка операции с деталями, статусы операций меняются со временем.
- Клиенты: мобильное приложение (iOS, Android) и веб. Версии приложения в маркете не обновляются принудительно.
- Операции приходят из трёх внутренних систем, часть полей доступна не для всех типов операций.
- Есть требование безопасности: не отдавать полные номера карт и счетов.

## Ограничения

- Нельзя сломать существующие версии приложения: минимум 12 месяцев поддержки.
- Приложение работает в плохих сетях: нужен кэш и корректное поведение при таймаутах.
- Команда бэкенда одна на веб и мобиль: решения должны быть общими, а не «специальный API под мобилку».

## Ожидаемые результаты

- Спецификация эндпоинтов: методы, пути, параметры запроса, состав ответов с типами и обязательностью, примеры.
- Правила пагинации и сортировки для больших списков.
- Единый формат ошибок: структура, коды, сообщения, что можно показывать пользователю.
- Политика версионирования: где версия (URL/заголовок), что считается ломающим изменением, как поддерживаем старые клиенты, сроки поддержки.
- Обратная совместимость: правила добавления/удаления полей, поведение клиента при неизвестном поле.
- НФТ: время ответа, лимиты, кэширование, офлайн-поведение, деградация.
- Процесс согласования контракта между мобильной командой и бэкендом, и как тестируем совместимость.

## Стартовые вкладки из БД

Заготовки сохранены дословно. Их наличие не делает все содержащиеся правила утверждёнными: противоречия разобраны в вопросах.

### Спецификация

Тип: doc.

```text
<h3>Эндпоинты</h3><h3>Пагинация</h3><h3>Формат ошибок</h3><h3>Версионирование</h3>
```

### Sequence: загрузка списка

Тип: plantuml.

```text
@startuml
autonumber
actor "Пользователь" as U
participant "Мобильное приложение" as APP
participant "API Gateway" as GW
participant "Сервис операций" as OPS

U -> APP: открыл "Мои операции"
APP -> GW: GET /v1/operations?limit=30\nIf-None-Match: ?
GW -> OPS: запрос
OPS --> GW: данные
GW --> APP: 200 / 304 / 4xx ?
APP --> U: список
@enduml

```
