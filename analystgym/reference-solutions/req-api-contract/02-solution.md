# Контракт API для мобильного приложения: версии, пагинация, ошибки

Задача: `req-api-contract`. Версия БД: **0**. Статус: **published**.

**Статус: условный черновик эталона, до ответов на вопросы.** Предложенные варианты и параметры не добавляют фактов к условию.

## Решение

1. Описать кандидат GET /v1/operations и GET /v1/operations/{id} с авторизацией владельца. Общая модель: стабильный id, type/status с определённой эволюцией, денежное значение с валютой и согласованной точностью, даты и условные детали. Конкретный состав утвердить по реальным источникам.

2. Выбрать устойчивую сортировку с уникальным tie-breaker и непрозрачным cursor, привязанным к фильтрам и контексту пользователя. Если данные изменяют порядок, задать snapshot/watermark либо честные правила обновления списка.

3. Единый объект ошибки включает стабильный code, безопасное сообщение, request_id и при необходимости ошибки полей/повторяемость. Разделить неавторизованность, отсутствие прав, недоступность источника и лимит.

4. Версионировать ломающие изменения и поддерживать старую схему минимум согласованные 12 месяцев. Добавление полей безопасно только для клиентов, которые терпимо их читают; добавление enum тоже проверить на старых сборках. Зафиксировать процесс согласования и контрактные проверки.

5. Кэш/ETag связывать с пользователем, фильтрами, правами и версией представления. При плохой сети показывать сохранённый срез с отметкой времени по согласованным правилам; частичный результат явно маркировать. Проверить выход и смену аккаунта.

## Как проверить качество результата

Старые поддерживаемые клиенты читают новый ответ без падения; нет чужих операций и утечек кэша. Проверить смену статуса между страницами, одинаковые даты, неизвестный тип, недоступность одного источника, 304 и выход из аккаунта. Числа НФТ — после согласования.

## Диагностика инцидентов в проектируемой системе

request_id, operation_id, псевдоним пользователя, contract_version, client_version, source_statuses, watermark, cache_result, error_code и длительности этапов; не логировать номера карт, cursor с чувствительными данными или полный ответ.

Это требования к решению учебного кейса. Изменения в работающий сервис этим пакетом не внесены.
