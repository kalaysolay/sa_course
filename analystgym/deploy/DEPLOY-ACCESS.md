# Ограниченный SSH-доступ для деплоя

Пользователь `deploy` не входит в `sudo` или `docker`. Root однократно
устанавливает `deploy-access.py` в `/usr/local/sbin/analystgym-deploy`.
Sudoers разрешает ровно три команды, с одним точным аргументом:

```bash
sudo -n /usr/local/sbin/analystgym-deploy status
sudo -n /usr/local/sbin/analystgym-deploy restart
sudo -n /usr/local/sbin/analystgym-deploy deploy
```

`status` показывает контейнеры выбранного проекта. `restart` перезапускает
только app. `deploy` приводит app к заранее одобренному образу/конфигурации,
без сборки, pull, запуска зависимостей и удаления чужих контейнеров.
Это не разрешение самостоятельно загружать любой код или образ.

## Установка

Перед первым запуском root проверяет SHA-256 переданного файла, копирует его
в собственный каталог и запускает `python3 -I /root/analystgym-deploy-setup.py --install`.
Копия должна быть проверена после копирования, а не до него: исходник в home
deploy может измениться. Саму установку нельзя разрешать через sudo.

Установщик ищет единственный Compose-проект с app и postgres по меткам
существующих контейнеров. При неоднозначности отказывается от установки.
Конфигурация разрешается с явными файлами и окружением root, без наследования
DOCKER_HOST/PATH/COMPOSE_* из shell deploy. Секретные значения не выводятся.
При app с host bind mounts, privileged, host namespaces или иными требующими
проверки возможностями установка отказывается их делегировать.

Текущий Image ID и разрешённая конфигурация сохраняются в
`/etc/analystgym-deploy/compose.json`, root:root 0600, каталог 0700.
Проект фиксируется в settings.json. Сохраняются имя проекта, полные имена
volumes/networks и абсолютные пути из разрешённого Compose. В app удаляется
build, image закрепляется локальным `sha256:...`, pull запрещается.
Контейнеры при установке не перезапускаются.

Если ни одного Compose-app нет, устанавливаются команды без активного релиза:
status объяснит отсутствие настройки, restart/deploy будут запрещены.
Root затем должен отдельно подготовить и проверить оба файла конфигурации;
повторная установка автоматически не перезаписывает существующую настройку.
Для первого запуска на новом VPS с существующим nginx предусмотрен
[FIRST-RELEASE.md](FIRST-RELEASE.md): он создаёт приложение и новую БД,
проверяет HTTPS и только затем активирует gateway.

## Утверждение нового релиза

Сборка/загрузка и одобрение нового образа остаются у root либо доверенного CI.
Один раз настроенные права не означают разрешение deploy менять Compose,
sudoers, системные службы, env, Dockerfile, образ или место его получения.
Root проверяет образ, создаёт бэкап БД, фиксирует его локальный Image ID в
защищённом compose.json и согласует миграции/откат. Прочие поля конфигурации
не меняются без отдельной проверки. Затем deploy может выполнить команду
deploy. Успешный выход Compose не заменяет проверку здоровья и миграций.

Для нового снимка строки с `$` экранируются как `$$`, поскольку интерполяция
уже выполнена. Env-файл runtime-команд — /dev/null; конфигурация не зависит
от текущего каталога или окружения deploy.

У пользователя есть право влиять на доступность app через restart/deploy и
на данные в пределах полномочий приложения. Он не получает прямое чтение
секретов, SQL, shell контейнера, произвольные docker/sudo, остановку postgres
или управление хостом. Команды и результат пишутся в authpriv/syslog с actor;
логи приложения специально не выдаются, так как могут содержать данные.

## Проверки

Без root и Docker: `python3 -I analystgym/deploy/test_deploy_access.py`.
После установки: `sudo -n -l`, затем status. Отдельно убедиться, что
`sudo -n ... status extra`, `sudo -n ... --install` и `sudo -n /usr/bin/docker ps`
запрещены. Для проверки прав не нужно перезапускать приложение.

Root отзывает доступ удалением `/etc/sudoers.d/analystgym-deploy`.
Удаление правила не удаляет пользователя и не останавливает контейнеры.
