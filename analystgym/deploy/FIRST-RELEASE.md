# Первый релиз на analystgym.pro

Сценарий для VPS, где уже работает `nginx-nginx-1` и его конфиги подключены
из `/data/nginx/user_conf.d` в `/etc/nginx/user_conf.d`. Нужны root, Python 3.10+,
Docker Compose и установленный gateway из DEPLOY-ACCESS.md. Это первый запуск
с новой БД, не обновление уже работающего приложения и не перенос локальной БД.

## Подготовка и запуск

Образ приложения собирается вне VPS с `gradle build`, проверяется на новой
БД и экспортируется через docker save. На VPS передаются архив образа и
`first-release.py`. Root копирует Python-файл в /root, сверяет SHA-256 копии,
затем запускает его с тремя параметрами:

```bash
python3 -I /root/analystgym-first-release.py \
  --archive /home/deploy/analystgym-release-image.tar \
  --sha256 SHA256_АРХИВА \
  --image sha256:CONFIG_DIGEST_ОБРАЗА
```

Контрольные суммы должны прийти из проверенной сборки, не вычисляться из
непроверенного удалённого файла перед запуском. Установщик сначала копирует
архив в root-каталог и сверяет получившуюся копию. Digest config проверяется
по manifest.json архива. После docker load фиксируется локальный Image ID:
он может отличаться между containerd и legacy Docker image store.

## Что изменяется

1. До изменений проверяются nginx-конфигурация, точный mount, единственный
   IPv4 gateway nginx, единственный HTTPS server нужного домена, отсутствие
   старого проекта/volume AnalystGym. Неизвестные location требуют проверки
   root вместо автоматического затирания. Текущий nginx должен быть исправен.
2. Создаётся /var/lib/analystgym-release (0700), сохраняется проверенный образ.
3. В /etc/analystgym-deploy/compose.json (0600) создаётся root-конфигурация:
   app с одобренным Image ID, новая PostgreSQL, постоянный named volume,
   внутренний backend и отдельная сеть egress для app. Секреты генерируются
   криптографически и не печатаются. PostgreSQL не имеет host-порта.
4. App публикуется на 127.0.0.1:18080 для проверок и на приватном bridge IP
   существующего nginx:18080 для проксирования. Публичный адрес VPS не слушает
   HTTP-порт приложения. Nginx не подключается к новой Docker-сети.
5. После readiness БД/приложения создаётся исходный pg_dump. Только затем
   сохраняется предыдущий nginx-конфиг и заменяется location / нужного TLS
   сервера. Сертификаты, их конфигурация, ACME и чужой virtual host сохраняются.
   Выполняются nginx -t, reload и внешние проверки HTTPS/каталога.
6. Если внешняя проверка неудачна, предыдущий nginx-конфиг восстанавливается
   и перезагружается. БД и диагностические файлы не удаляются. После успеха
   публикуется settings.json: ограниченный deploy получает рабочую привязку.

По умолчанию REVIEW_ENGINE=mock, SMTP/Google-вход и fake-оплаты выключены.
Первый администратор не создаётся автоматически: email/пароль владелец
задаёт отдельной root-командой --bootstrap-admin по DEPLOY.md. Реальные
ключи LLM/SMTP вводятся только в защищённой конфигурации под root.

При смене Docker-сети самого nginx её gateway может измениться. Root должен
обновить соответствующий bind-порт app и upstream nginx вместе, предварительно
проверив новый адрес. Простая пересборка nginx-контейнера в той же сети этого
не требует. Новые версии приложения выпускаются через одобрение нового Image ID.

## Ошибки и проверка

Повторный запуск автоматически запрещён при наличии состояния или БД:
это защита от повторной генерации паролей и случайного запуска поверх данных.
После прерывания root проверяет Compose, состояние БД и nginx, затем выбирает
завершение установки или восстановление вручную; удалять volume нельзя.

Проверки установщика: `python3 -I analystgym/deploy/test_first_release.py`.
После установки из PowerShell: `ssh analystgym-vps 'sudo -n /usr/local/sbin/analystgym-deploy status'`.
Отдельно проверяются https://analystgym.pro/actuator/health и /api/tasks.
Первый бэкап не заменяет настройку регулярных резервных копий и проверку restore.
