# AnalystGym — спецификация продукта (основа Java-приложения)

Версия: 0.1 (по состоянию макета `tasks-mockup/`).

Уточнение интерфейса от 2026-10-18:
- Вкладки решения обведены тонкой рамкой, объединяющей название и меню.
  Активная вкладка выделяется мягкой акцентной заливкой, рамкой, нижней линией
  и более плотным текстом; неактивные сливаются с фоном полосы вкладок.
  Служебная подпись «простой WYSIWYG» убрана; состояние сохранения показывается
  внизу редактора.
- Добавление части решения: «Документ» или «Схема». Для схемы выбирается
  последовательность/процесс/состояния; по умолчанию PlantUML, Mermaid —
  в дополнительных настройках. Действия вкладки находятся в её меню «⋯».
  Старые вкладки и типы API сохраняются; оба агента получают все документы
  и исходники схем независимо от активной вкладки. Общий промпт уточняет
  совместное чтение, равноправие форматов и отсутствие зачёта за один шаблон.
  План и анализ влияния: `solution-editor-plan.md`.
- Кнопка диаграммы явно скрывает/показывает предпросмотр и сообщает его состояние
  через aria-expanded. «Обновить» обозначено круговой стрелкой.
- При фокусе в правой панели решения на экранах шире 1080px её ширина плавно
  увеличивается на 10% относительно исходной. При работе с кнопками панели
  ширина сохраняется, при уходе фокуса — возвращается. На узких экранах
  расширения нет; при prefers-reduced-motion анимация отключена.
- Серая тема затемнена; вторичный текст сохраняет читаемость.
- Бренд главной страницы занимает отдельную строку в потоке документа:
  заголовок «Тренируйся» не может оказаться под логотипом при изменении ширины.
- На экранах до 860px шапка состоит из бренда/меню и строки действий,
  обе строки начинаются слева. Раскрытое меню находится под всей шапкой.
- Дублирующий пункт «Кабинет» убран из основной навигации тренажёра;
  после входа профиль открывается по имени рядом с кнопкой выхода.

Уточнение реализации от 2026-10-17 — пакет аудита 11–13 (V15):

- UC-D01–D03: `POST /api/assessment/runs` принимает заранее сохранённый UUID
  прохождения. При старте фиксируются весь банк (включая ответы/объяснения,
  недоступные клиенту до финиша) и его SHA-256. Повтор старта возвращает тот же
  банк. `PUT /runs/{id}` сохраняет ответы, отметки и позицию с обязательной
  `version`; конфликт устройств — 409 `assessment_conflict`, без перезаписи.
  `POST /runs/{id}/finish` считает по снимку и сохраняет канонический результат;
  повтор с теми же ответами возвращает готовый результат без нового замера.
  Старый POST `/submissions` отвечает 410 `assessment_run_required`.
- Авторизованный пользователь загружает активное прохождение через
  `GET /runs/current`, результаты — из истории аккаунта. Гостю нужен отдельный
  случайный секрет в `X-Assessment-Token`; в БД хранится только SHA-256, срок
  гостевого доступа — 7 дней (ASSESSMENT_GUEST_DAYS, 1–30). Секрет не находится
  в URL. После входа студент явно привязывает гостевое прохождение через
  `POST /runs/{id}/claim`; чужой аккаунт не может забрать уже привязанный тест.
  Повтор привязки владельцем безопасен; завершённый замер создаётся ровно один
  раз. История доступна на другом устройстве без локального результата.
- В server-режиме клиент берёт вопросы и результат только из API. Локальная
  копия хранит неподтверждённый прогресс; состояния «сохранено», «ожидает»,
  «ошибка», «конфликт» видны. Записи сериализуются, поздний ответ не затирает
  новые ответы. При конфликте студент выбирает свою или серверную копию.
  Если другое устройство завершило тест, неподтверждённые локальные ответы
  остаются отдельной копией, результат берётся с сервера. Ошибка финиша не
  подменяется Scoring.compute. Embedded-диагностика обозначена как демо.
  Ответы старого аккаунта не применяются после переключения. Привязка гостя
  сохраняет неподтверждённую копию; истёкшее прохождение позволяет начать новое,
  оставив локальный снимок прежнего. В сборку сервера встроенный questions.js
  с ответами не включается. Неподтверждённые отзывы с обещаниями трудоустройства
  на странице практики заменены пояснениями об использовании результата.
- UC-S08/UC-Q03: жалоба относится к `reviewRevision`, сохраняет исходный JSON
  и реальные версии промптов. Повторная открытая жалоба на ту же ревизию — 409.
  Сотрудник может взять в работу, отклонить с объяснением, исправить состояния
  критериев с пересчётом балла либо назначить повторное ревью. Закрыть resolved
  одним текстом нельзя. Для исправления/отклонения/повтора нужна причина
  10–2000 символов. Роли проверяются сервером, конфликт формы сохраняет поля.
- `reviews` содержит актуальный результат и номер ревизии; `review_revisions`
  сохраняет каждый предыдущий результат, контекст, автора и причину.
  Сотрудник меняет состояния всей рубрики, не вводит произвольный числовой
  балл. `human-review/v1` явно обозначает ручной разбор. История доступна
  владельцу через `/api/attempts/{id}/revisions` и персоналу качества.
- Повторное ревью — новая попытка с прежним решением/условием и выбранными
  заново текущими промптами/маршрутами. До её завершения жалоба остаётся review.
  Восстанавливаемый сверщик переносит готовый результат в новую ревизию
  исходного ревью и закрывает жалобу. Технический сбой/конфликт с другим
  исправлением оставляет её в работе (`recheck_failed`/`recheck_conflict`).
  Сохраняются действия сотрудника и автоматической финализации.
- Уведомление в кабинете и запись для SMTP создаются в той же транзакции,
  что и готовность/исправление ревью. `/api/notifications` возвращает только
  свои записи. SMTP работает отдельно от транзакции и потока heartbeat,
  с lease, уникальным ключом события и ограниченными повторами (5, 30/60/120… с).
  При APP_MAIL_ENABLED=false письма ждут в очереди, уведомление в кабинете
  уже доступно. Неопределённый исход SMTP может дать повтор письма; повтор
  исправления результата исключён. Адрес/SMTP настраиваются через env.
- Диагностика показывает знания по конкретному набору вопросов, ошибки,
  пропуски и учебный балл. Убраны обещания оффера, рынка, сроков роста и
  категоричное присвоение Junior/Middle/Senior/Lead. Старые внутренние ID
  диапазонов сохранены для совместимости; подписи теперь описывают знания.
- Mock — `mock-agents/v2`: поиск слов явно назван демонстрацией, общий балл
  не выше 45/100, агентский — не выше 4/10. Маркеры могут встречаться в
  отрицании/перечне терминов; это не подтверждение смысла. Маршруты mock://
  в LLM-стенде также обозначаются `llm-demo/v2` и получают демо-ограничение.
  LLM-оценка обозначена предварительной, `qualityStatus=uncalibrated`.
- Контрольный набор содержит развёрнутое, слабое, противоречивое решение,
  перечисление терминов и попытку изменить инструкции. Есть сравнение с
  разметкой методиста по каждому критерию и диапазону балла с контекстом модели.
  По подтверждению владельца готовых разборов методиста нет; прогон живой LLM не выполнялся:
  отсутствие разметки считается незавершённой проверкой, а не успехом.
  Порядок калибровки: `review-calibration.md`.

Проверки: реальные PostgreSQL-транзакции и миграция V15, неизменность банка,
конфликт устройств, гостевой секрет/срок/привязка, история, ручная коррекция,
повторное ревью и его сбой, версии и outbox/повтор SMTP; клиентские регрессии,
контрольный набор, браузерные сценарии и Gradle build.

Уточнение реализации от 2026-10-17 — пакет аудита 7–10:

- UC-SYS01: один вызов LLM возвращает плоский JSON одного агента:
  `criteria`, `narrative`, `covered`, `missed`, `improve`, `questions`.
  Сервер добавляет обязательный контракт к выбранной редакции промпта.
  Агент получает полное условие, полную рубрику и `criteriaToReview` своего
  фокуса. Каждый свой критерий обязателен ровно один раз, чужие запрещены.
  Для hit/partial нужна цитата из решения (нормализуются регистр/пробелы).
  Наличие цитаты не доказывает правильность вывода модели. Балл считает код.
  Невалидная схема допускает один корректирующий вызов, затем fallback;
  все обращения подчиняются общему бюджету попытки.
- Решение передаётся отдельно от system-инструкций, после удаления
  HTML-разметки документа и маскирования email/телефонов. Диаграммы входят
  целиком. Молчаливой обрезки нет: по умолчанию максимум 20 000 символов
  исходного содержимого вкладок и 64 000 UTF-8 байтов system+user на вызов.
  Превышение до приёма — 413 `solution_too_large`,
  `review_context_too_large` или `review_context_over_budget`; черновик остаётся.
  `GET /api/review/limits` возвращает действующие ограничения.
- UC-S03: обязательны `Idempotency-Key` (1–64 символа), `taskVersion` и
  неизменяемое тело. Повтор ключа/тела возвращает исходную попытку, включая
  уже завершённую и снятую с публикации задачу. Другое тело — 409
  `idempotency_conflict`. `GET /api/attempts/submissions/{key}` восстанавливает
  ответ только владельцу. Браузер сохраняет ключ и снимок до POST в пространстве
  аккаунта. При сети/5xx ключ остаётся; после перезагрузки выполняется GET,
  повтор POST требует действия студента. Если черновик изменён, студент явно
  выбирает восстановление прошлого снимка; новые правки остаются. Web Locks
  объединяет отправки соседних вкладок поддерживающего браузера; серверная
  идемпотентность защищает одинаковый ключ во всех клиентах.
- Квота Free: число различных задач со статусом queued/in_review/reviewed.
  Проверка квоты, создание попытки со снимками и job атомарны под блокировкой
  пользователя. Параллельные новые задачи не обходят лимит. Доработка той же
  задачи не занимает ещё одно место; terminal failed освобождает место, если
  нет другой принятой/готовой попытки по этой задаче.
- UC-SYS01/UC-S04: захват job через SKIP LOCKED и ограниченный lease с уникальным
  токеном. Heartbeat продлевает захват независимо от HTTP. Истёкший job снова
  доступен; старый токен не позволяет писать стадию, расход или результат.
  HTTP выполняется вне транзакции БД. По умолчанию 2 обработки на инстанс,
  lease 30 с, heartbeat 1 с, до 3 захватов, паузы повторов 2/4 с.
  429/5xx/сеть допускают повтор; исчерпанный бюджет и схема после коррекций —
  failed. Polling показывает реальные стадии: очередь, ожидание повтора,
  агент, вердикт, готово. Потеря связи восстанавливает статус той же проверки.
- При submit сохраняются версия и полное публичное тело задачи, рубрика,
  выбранные версии/тексты промптов, конфиги агентов и маршрутов провайдеров,
  модели и лимиты. Правки админки не меняют принятую проверку. В `review_calls`
  до HTTP фиксируются точные сообщения и резерв, после — сырой ответ,
  фактическая модель, usage, валидация или ошибка. Ключ API не сохраняется:
  только имя env. Готовая часть агента повторно используется при восстановлении;
  прерванный вызов остаётся unknown.
- Бюджет: максимум 6 вызовов и 160 000 учётных токенов на попытку, включая
  fallback, корректировки и восстановление. До вызова резервируются
  `UTF-8 байты system+user + 1024 + maxOutputTokens`; в HTTP всегда передаётся
  `max_tokens` (по умолчанию 2000). Известный usage заменяет резерв даже у
  невалидного ответа; сеть/отсутствие usage/потеря воркера сохраняют весь резерв.
  Невозможный usage фиксируется и завершает проверку управляемой ошибкой.
  Это консервативный технический бюджет, не точный токенизатор модели и не
  гарантия денежного счёта провайдера. Ответ HTTP ограничен 1 МиБ до JSON.
- `GET /api/attempts/{id}/context`: владелец получает сохранённое условие без
  эталона и служебных промптов; в ревью есть кнопка «Условие этой попытки».
  Персонал качества открывает полный контекст и журнал через
  `/api/admin/attempts/{id}/context`. Другой студент не получает эти данные.
  V14 сохраняет готовые старые ревью, отсутствующий контекст не выдумывается.
  Старые незавершённые попытки без плана переходят в failed с
  `legacy_review_requires_resubmit`; студент отправляет решение заново.

Проверки: PostgreSQL/Flyway, конкурентные submit/квота, lease/backoff,
устаревший воркер, снимки и доступ, seed-промпты через локальный HTTP-стаб,
полный длинный текст, независимые агенты, коррекция схемы, сохранённый агент,
unknown-расход и бюджет; unit/ArchUnit, клиентские и браузерные регрессии.

Уточнение реализации от 2026-10-17 — пакет аудита 5–6:

- Серверный каталог и словари полностью заменяются ответами API, включая
  пустые массивы. Локальные admin-overrides действуют только в статическом
  макете. Ошибка API показывает ошибку с повтором, без подмены демоданными.
- Рабочее место читает условие, вкладки, рубрику, подсказки и вопросы через
  `/api/tasks/{id}/detail`. В JAR нет `data-tasks-1.js`/`data-tasks-2.js`
  с эталонами. Статический макет загружает их динамически в embedded-режиме.
- Эталон загружается отдельно через `/reference`: доступ даёт только своя
  серверная reviewed-попытка. Локальная история не открывает серверный эталон.
  HTML условия, эталона и редактора выводится через список разрешённых тегов,
  без скриптов, событий и сторонних iframe.
- Архив исключается из каталога и публичного состава подборок; прямые ссылки
  на карточку/детали/эталон дают 404. В админке состав подборки сохраняется.
- Detail возвращает `version`, submit требует `taskVersion`. Если задача
  изменилась после открытия, ответ 409 приходит до создания попытки; черновик
  сохраняется, нужно обновить страницу и прочитать новое условие. Уже принятый
  Idempotency-Key возвращает исходную попытку и после правки задачи.
- Админка работает с API: METHODIST — контент и качество; REVIEWER — качество;
  LLM_ADMIN — провайдеры, агенты, промпты; SUPERADMIN — всё, роли и аудит.
  Сервер проверяет роль при каждом запросе. Нет доступа — нет локальной подмены.
- Создание заполненной формы задачи атомарно, новая задача всегда draft.
  Workflow: draft → review → published → archived; review → draft,
  archived → draft. Публикация и правка published требуют brief, goal,
  непустые deliverables, хотя бы один критерий с уникальным ID, весом 1–10,
  фокусом и маркерами, эталон doc и стартовые вкладки. JSON проверяется по типам
  и размерам. Состав подборок редактируется отдельной формой подборки.
- Доступны ревизии, экспорт одной задачи, импорт новой задачи и серверный
  симулятор детерминированного скоринга рубрики (без вызова платной LLM).
  Редактор сохраняет ID критериев, числовые веса и обе диаграммы эталона.
- V13 добавляет JPA-версии задач, меток, подборок, уровней, провайдеров,
  агентов, редакций промптов и жалоб. Изменение существующей записи требует
  `version`; устаревшая/отсутствующая версия даёт 409. При ошибке поля формы
  остаются на экране: их можно скопировать перед обновлением данных.
  Смена роли проверяет `expectedRole` под блокировкой пользователя.
  При удалении метки/подборки версия передаётся query-параметром `version`.
- Новая редакция промпта создаётся с 0% трафика. Рабочий текст нельзя менять
  на месте — нужно создать новую редакцию. Promote назначает 100%, остальным
  0%. При настройке доли остаток получает активная редакция, сумма — 100%.
  Номера редакций и перераспределение сериализованы по промпту.
- KPI качества берутся из БД; нет оценок — «—». Лента решений подписана
  «Последние 100 решений». В списке задач агрегаты по каждой задаче пока «—».
  Демопроценты решаемости/популярности и сортировки по ним скрыты на серверной
  витрине; реальные агрегаты остаются отдельной доработкой.

  создаётся оператором отдельной серверной командой `--bootstrap-admin`;
  существующий email команда не повышает, старый `APP_ADMIN_EMAILS` не действует.
- Access/refresh имеют разные назначения, уникальный jti и sid. API проверяет
  существование непогашенной сессии. Ротация, выход и смена пароля атомарны
  относительно операций того же пользователя; смена/сброс завершает все сессии.
  Пароль: минимум 8 символов, максимум 72 байта UTF-8, непустой по смыслу.
- Клиент автоматически восстанавливает сессию при 401, объединяет параллельные
  refresh (между вкладками — Web Locks, когда доступны) и повторяет исходный
  запрос с тем же телом и ключом. Сетевые ошибки мутаций не ретраятся.
  Окончательный отказ входа сохраняет черновик и не запускает локальное ревью.
- Хранилище `sa-trainer:v2:<userId>` отделено от `sa-trainer:v2:guest`.
  При входе предлагается перенос явно гостевых черновиков без замены существующих.
  Старый общий `sa-trainer:v1` остаётся нетронутым и не присваивается аккаунтам:
  его владельца установить нельзя. Перенос диагностики/попыток из guest не выполняется.
- Смена аккаунта в соседней вкладке сохраняет текущий редактор и перезагружает
  страницу; X-Account-ID дополнительно запрещает отправку данных прежнего аккаунта
  под новыми куками. Чтение состояния страниц начинается после определения аккаунта.
- Черновики имеют серверную версию. PUT принимает `version` (null для нового),
  GET/PUT возвращают её; устаревшая запись — 409. При расхождении сохранённых
  версий клиент показывает даты и предлагает продолжить локальную либо серверную.
- Локальное демо работает при file:// или отсутствии API (health=404).
  Ошибка сервера/каталога не переводит серверный сценарий в mock.
- Регистрация и операции паролей имеют отдельные лимиты запросов. Доверие
  proxy-заголовкам обеспечивает контейнер; произвольный X-Forwarded-For код не читает.

После обновления старые JWT требуют повторного входа (миграция V11).
Статус: рабочий документ. Макет — кликабельный прототип UX и поведения;
этот документ фиксирует, ЧТО строим, для КОГО и КАК должно работать.

Связанные документы: `docs/admin-guide.md` (админка), `TODO.md` (отложенное),
`README.md` (карта макета и поддоменов).

## 1. Цели проекта

### 1.1. Бизнес-цели
1. **Сначала спрос, потом деньги:** paywall тренажёра заменён предзаписью
   на Pro (email + телефон, таблица `waitlist`). Платная подписка Pro
   (помесячно/год) + разовые покупки курсов включаются после набора
   предзаписи. Цель MVP: измеримая предзапись вместо первых 100 платящих.
   Бэкенд биллинга сохранён (квота Free — 2 задачи, 402 ведёт на предзапись).
2. **Дешёвое привлечение:** бесплатная диагностика уровня как магнит
   (цель: ≥30% посетителей хаба проходят диагностику).
3. **Удержание через прогресс:** студент видит измеримый рост (повторная
   диагностика, баллы ревью, % прохождения) — цель: ≥40% вернувшихся
   в течение 14 дней после первого ревью.

### 1.2. Продуктовые цели
1. Готовить к собеседованию **практикой, а не теорией**: решение пишется
   как на работе, разбирается как на собесе.
2. Оценка — **качество решения, а не «верно/неверно»**: что учтено,
   что упущено, почему (не) сработает, что спросят дальше.
3. Методист правит контент без разработчиков: задачи, рубрики, промпты,
   подборки — всё через админку с версионированием.
4. Каждое ревью воспроизводимо: известно, какая версия рубрики, промпта
   и агента его выдала (иначе невозможен тюнинг).

### 1.3. Не-цели MVP
Мобильные приложения, маркетплейс авторов, live-менторство, LMS-интеграции
(SСORM/xAPI), мультиязычность (только RU), офлайн-режим.

## 2. Описание продукта

### 2.1. Состав
| Продукт | Домен (прод) | Макет | Суть |
|---|---|---|---|
| Хаб-развилка | `analystgym.ru` | `index.html` | Два полуэкрана (Практика / Курсы) + магнит-диагностика, без шапки/подвала |
| Тренажёр (Practice) | `practice.analystgym.ru` | `practice.html`, `catalog.html`, `collections.html`, `task.html`, `assessment.html`, `results.html` | Задачи с ревью ИИ-агентов + диагностика |
| Курсы (Course) | `course.analystgym.ru` | `courses.html`, `course.html` | Уроки по модулям, прогресс, разовая оплата |
| Админка | внутр. | `admin.html` | Задачи, качество (дашборд/решения/пользователи/жалобы), агенты, версии, справочники |

### 2.2. Акторы и роли
- **Гость** — видит хаб, каталоги, бесплатный контент; решения и диагностика
  требуют... (в MVP без регистрации, состояние в браузере; в Java — аккаунт).
- **Студент** — зарегистрированный пользователь: решения, попытки, прогресс
  курсов, диагностика, жалобы.
- **Методист** — создаёт и правит задачи, рубрики, подборки, справочники;
  разбирает жалобы; правит контент, не код.
- **Ревьюер качества** — разбирает попытки и жалобы, подтверждает ревью
  (роль заложена в модель, отдельный экран — позже).
- **Админ LLM-инфраструктуры** — агенты, промпты, версии, трафик A/B.
- **Супер-админ** — роли доступа, лог действий (заложено, экраны — позже).
- **Система** — пайплайн ревью, подсчёт диагностики, фоновые сверки.

### 2.3. Ключевые принципы
1. Рубрика — контракт оценки; текст рубрики виден студенту (кроме эталона).
2. Эталон виден только после ревью.
3. Правка опубликованного = новая ревизия, тихо не правим.
4. Студентам виден только статус `опубликована`.
5. Диагностика — магнит в контенте, не пункт навигации.
6. Продукты разделены (свои навигации, своя монетизация), связаны
   кросс-ссылками, общим аккаунтом и диагностикой.
7. Логотип везде ведёт на хаб платформы (`index.html`), а не на главную
   продукта; из футеров обоих продуктов есть ссылка «AnalystGym — платформа».
8. Мобильная навигация: на ≤860px меню сворачивается в бургер (выпадашка,
   закрытие по ссылке/мимо/Escape); шапка ужата (у кнопки темы остаётся
   только значок). Favicon (`logo.png`) подключён на всех страницах.

## 3. Юзкейсы

Формат: предусловия → шаги → исключения → постусловия → привязка к макету
(что переиспользовать при кодинге).

### 3.1. Студент — тренажёр

#### UC-S01. Просмотр каталога задач
- **Предусловия:** нет.
- **Сценарий:** 1. Открыть каталог. 2. Фильтровать по уровню/меткам/статусу,
  искать, сортировать. 3. Открыть задачу. Фильтры — в URL (ссылки шарингуются).
- **Постусловия:** —. **Макет:** `catalog.html`, `catalog.js`.

#### UC-S02. Прохождение подборки
- **Сценарий:** 1. Открыть подборку (домен). 2. Видеть состав, уровни,
  свой прогресс. 3. Кнопка ведёт на первую нерешённую задачу.
- **Макет:** `collections.html`.

#### UC-S03. Написание решения
- **Сценарий:** 1. Слева условие (включая критерии оценки — что спросят).
  2. Справа вкладки: документ (WYSIWYG), PlantUML, Mermaid (+добавить/
  переименовать/дублировать/закрыть). 3. Диаграммы рендерятся живьём.
  4. Черновик автосохраняется. 5. Подсказки открываются по одной, эталон
  скрыт до ревью.
- **Исключения:** E1 — пустое решение: отправка разрешена, но с
  предупреждением в диалоге подтверждения.
- **Макет:** `task.html`, `task.js`.

#### UC-S04. Отправка решения на ревью
- **Предусловия:** черновик существует.
- **Сценарий:** 1. «Отправить решение» → диалог со сводкой (вкладки, слова,
  диаграммы). 2. Подтвердить. 3. Видеть живой прогресс двух агентов
  (стадии проверки). 4. Автоскролл к готовому ответу.
- **Постусловия:** попытка сохранена со статусом, затем с ревью; черновик цел.
- **Макет:** `task.js` (askSubmit/submit/startReview), `review-engine.js`.

#### UC-S05. Просмотр ревью
- **Сценарий:** 1. Вердикт: грейд 1–5 + балл/100 + расшифровка «почему».
  2. Два агента: оценка/10, «учтено» (с цитатами из решения), «не учтено»
  (с объяснением последствий), нарратив «почему (не) решает задачу»,
  «как усилить», вопросы интервьюера. 3. Разбор по критериям рубрики.
  4. «Что потренировать дальше» (ссылки на задачи).
- **Макет:** `task.js` (renderReview), структура `ReviewResult` в движке.

#### UC-S06. История и повторные попытки
- **Сценарий:** список попыток с баллами, переключение между ревью,
  «Доработать и отправить снова». Динамика баллов видна.
- **Макет:** `#attemptsSection` в `task.js`.

#### UC-S07. Просмотр эталона
- **Предусловия:** есть хотя бы одно ревью по задаче (иначе — спойлер
  убивает тренировку).
- **Сценарий:** раскрыть «Эталонное решение автора» (документ + схемы).
- **Макет:** `#authorFold` в `task.js`.

#### UC-S08. Оспаривание ревью (жалоба)
- **Сценарий:** 1. Кнопка «Оспорить» в карточке ревью. 2. Причина текстом.
  3. Жалоба уходит в очередь админки со ссылкой на попытку, задачу
  и версию промпта.
- **Постусловия:** жалоба в статусе «Новая». **Макет:** частично (очередь
  и разбор есть в админке; кнопку в карточке ревью добавить).

### 3.2. Студент — диагностика

#### UC-D01. Прохождение диагностики
- **Сценарий:** 40 вопросов, один на экран; навигация стрелками/цифрами/точками,
  флаг «сомневаюсь», автопереход после ответа, возврат и правки, выход
  с сохранением прогресса, подтверждение при пропусках/завершении.
- **Постусловия:** результат посчитан и сохранён.
- **Макет:** `assessment.html`, `assessment.js`, `scoring.js`.

#### UC-D02. Просмотр результата
- **Сценарий:** грейд + балл, кольцо, профиль по 7 компетенциям (сильные зоны
  / пробелы), интерпретация, «взгляд работодателя», план прокачки
  (задачи под пробелы), разбор каждого ответа, копирование результата.
  Кнопка «К задачам по моему уровню» ведёт в каталог с предустановленными
  метками двух главных пробелов (`catalog.html?tag=...`), а не в общий список.
- **Макет:** `results.html`, `results.js` (levelCatalogUrl).

#### UC-D03. Повторная диагностика
- **Сценарий:** перепройти в любой момент; прошлый результат виден до старта;
  новый перезаписывает (история замеров — в продукте).
- **Макет:** `assessment.html` (блок «Предыдущая диагностика»).

### 3.3. Студент — курсы

#### UC-C01. Каталог курсов
- **Сценарий:** карточки (лого, название, цена/скидка/бесплатно, длительность,
  уровень, прогресс, CTA по состоянию).
- **Макет:** `courses.html`, `courses.js`.

#### UC-C02. Страница-обзор курса
- **Сценарий:** описание, outcomes, мета, программа по модулям, цена,
  CTA («Начать/Продолжить/Пройти заново» → нужный урок).
- **Правило:** `course.html?id=X` без `&lesson=` — всегда обзор.
- **Макет:** `course.js` (renderAbout).

#### UC-C03. Прохождение урока
- **Сценарий:** сайдбар модулей (счётчики, текущий подсвечен и подкручен
  в видимость), контент, виды «Лекция / Упражнения / Артефакты» (переключатель
  в шапке + диплинки `?view=`), ответы под катом, отметка «пройден»,
  навигация prev/next.
- **Макет:** `course.html`, `course.js`, `md.js`, контент из `output/`.

#### UC-C04. Демо-доступ и покупка
- **Сценарий:** неоплаченные уроки показывают paywall (цена, что входит).
  «Оформить» → оплата (в продукте) → доступ ко всем урокам. В макете —
  демо-разблокировка в один клик.
- **Макет:** paywall + `#buyBtn` в `course.js`.

#### UC-C05. Прогресс курса
- **Сценарий:** счётчик и бар в шапке курса, статусы уроков (✓/🔒/номер),
  прогресс на карточке каталога.
- **Макет:** `Store.courseProgress`, `courses.js`, `course.js`.

### 3.4. Методист — контент

#### UC-M01. Создание задачи
- **Сценарий:** «+ Новая задача» → название → ID генерируется транслитом
  (уникализация `-2`, `-3`) → статус `черновик` → заполнение → сохранить.
- **Макет:** `admin-tasks.js` (blankTask, slugify).

#### UC-M02. Редактирование задачи
- **Сценарий:** пять аккордеонов (Основное, Условие, Рубрика, Контент+эталон,
  Симулятор). Сохранение = новая ревизия, сразу влияет на продукт
  (в Java — через workflow публикации, см. UC-M04).
- **Макет:** `admin-tasks.js` (renderCard/collectForm).

#### UC-M03. Управление рубрикой
- **Сценарий:** CRUD критериев: название, вес 1–10, зона sa/arch, маркеры,
  `why`, флаг critical. Проверка — симулятором (UC-M05).
- **Макет:** paintRubric/collectRubric.

#### UC-M04. Жизненный цикл задачи
- **Сценарий:** смена статуса `черновик → на ревью → опубликована → архив`
  (из списка или карточки). Студентам видна только опубликованная.
  Архивная пропадает из каталога, история попыток сохраняется.
- **Макет:** статусные селекты, `Store.taskStatus`.

#### UC-M05. Симулятор скоринга
- **Сценарий:** вставить текст (или подставить эталон) → «Проверить» → балл
  + таблица попаданий по критериям + оценки агентов. Используется для
  отладки рубрики до публикации.
- **Макет:** панель симулятора, `ReviewEngine.buildReview`.

#### UC-M06. Управление подборками
- **Сценарий:** CRUD подборки: название, описание, иконка, упорядоченный
  состав (чекбоксы в карточке задачи двусторонне синхронизируются),
  видимость.
- **Макет:** существующий раздел «Подборки».

#### UC-M07. Справочники (метки, уровни)
- **Сценарий:** CRUD меток (название, ID, категория, синонимы, вкл/выкл);
  уровни — переименование/описание без удаления. Скрытие вместо удаления
  занятых меток. Поиск по меткам, выбранные — первые.
- **Макет:** разделы «Метки», «Уровни».

#### UC-M08. Превью глазами студента
- **Сценарий:** из списка/карточки — открыть задачу как её видит студент.
- **Макет:** ссылки `task.html?id=`.

#### UC-M09. Импорт/экспорт задач (JSON)
- **Сценарий:** выгрузка задачи/каталога в JSON (наполнение, бэкап, перенос
  между стендами); загрузка с валидацией схемы.
- **Макет:** частично (экспорт состояния в «Данных макета»); полный — в Java.

### 3.5. Качество

#### UC-Q01. Дашборд
- **Сценарий:** KPI, «Требуют внимания» (жалобы + просевшие баллы → в задачи),
  топ miss-критериев (сигнал чинить контент), последние жалобы.
- **Макет:** `admin-ops.js` (renderDashboard).

#### UC-Q02. Разбор попытки
- **Сценарий:** фильтр по задаче → таблица попыток → модалка «решение рядом
  с ревью» (текст, диаграммы, агенты, критерии) → переходы в рубрику/задачу.
- **Макет:** renderAttempts/openAttemptModal.

#### UC-Q03. Разбор жалобы
- **Сценарий:** очередь с фильтром статусов → карточка (фрагмент решения,
  причина, версия промпта) → итог разбора → статус
  (`Новая → Разбираем → Решена/Отклонена`) → ссылки в рубрику/задачу.
- **Макет:** renderComplaints/openComplaintModal.

#### UC-Q04. Карточка студента
- **Сценарий:** список (роль, уровень, попытки, средний балл, активность) →
  карточка с последними попытками. Контекст для разбора жалоб.
- **Макет:** renderUsers (демо-данные).

### 3.6. LLM-инфраструктура

#### UC-L01. Управление агентами
- **Сценарий:** карточка агента (имя, роль, фокус — редактируется построчно,
  модель, связанный промпт с активной версией), тумблер участия в пайплайне.
- **Макет:** renderAgents, `Store.agents/saveAgent`.

#### UC-L02. Редактирование текста промпта
- **Сценарий:** кнопка «Текст» в строке версии → редактор с подсказкой
  плейсхолдеров (`solution`, `rubric`, `task_title`, `criteria`) → сохранить.
- **Макет:** data-version-text модалка.

#### UC-L03. Новая версия промпта
- **Сценарий:** «+ Новая версия» → номер авто (max+1), копирование текста
  из выбранной, обязательный changelog, стартовый трафик (0 = архив,
  >0 = канарейка) → создать.
- **Макет:** data-new-version модалка, `Store.addPromptVersion`.

#### UC-L04. Управление трафиком A/B
- **Сценарий:** число % в строке версии, сумма по промпту = 100%.
  Канарейка → сравнение баллов/жалоб → promote или откат.
- **Макет:** data-traffic, `Store.setPromptTraffic`.

#### UC-L05. Promote версии
- **Сценарий:** «Сделать активной» → подтверждение → 100% трафика,
  остальные в архив, текст/changelog не затираются.

#### UC-L06. Ревизии рубрик
- **Сценарий:** таблица по задачам (критериев, v1/v2, дата) → переход

## 4. Модель данных (кратко, детали — в коде макета)

- **Task**: id, title, level→Level, tags[]→Tag, statement{brief,context,goal,
  inputs,deliverables,constraints,interview}, starterTabs[], rubric:
  Criterion{id,title,weight 1–10,focus,keywords[],why,critical}, hints[],
  interviewQuestions[], authorSolution{doc}, status, timeMin, createdAt,
  updatedAt, stats (derived).
- **Collection**: id, title, tagline, description, icon, audience,
  taskIds[] (ordered), active.
- **Tag / Level / Competency / Grade**: справочники (`data-core.js`).
- **Attempt**: id, taskId, userId, submittedAt, status, tabs[] (решение),
  review: **ReviewResult** {grade, summary, why[], criteria[{state,
  matched[],evidence}], agents[{score,covered[],missed[],narrative,
  improve[],questions}], stats, engine, rubricVersion, promptVersions}.
- **Complaint**: id, taskId, attemptId?, userId, score, reason, excerpt,
  promptVersion, status, resolution, createdAt.
- **User**: id, name, role (SA/BA), level, stats (derived).
- **Agent**: id, name, role, initials, checks[], model, enabled,
  promptKey.
- **Prompt**: key, name, agent; **PromptVersion**: v, status
  (active/canary/archived), traffic %, text, changelog, model, updatedAt.
- **Course/Lesson**: course{id,title,price,modules[{sections[{lessons[]}]}]},
  progress per user, owned (paywall).
- **Assessment**: answers{qId:option}, flags, result{score, grade,
  byCompetency[], strengths, gaps, detail[]}.

Прототипы структур: `assets/js/data-*.js` (данные), `store.js` (состояние
и слияния), `review-engine.js` (контракт `ReviewResult` — главный кандидат
в DTO Java-бэка).

## 5. Нефункциональные требования (MVP)

1. Время ответа каталога/задачи p95 ≤ 500 мс (без ревью); ревью — асинхронно,
   прогресс виден живьём, результат переживает перезагрузку.
2. Ревью идемпотентно по попытке; повторная отправка не плодит ревью.
3. Все мутации контента — через ревизии с автором и временем.
4. Персданные: минимум (имя, контакт для оплаты), удаление по запросу.
5. Оплата (вне ядра MVP, интерфейс): провайдер за адаптером; валюты RUB/KZT;
   webhooks идемпотентны.
6. Стек-ориентир: Java 21, Spring Boot, PostgreSQL (+Flyway), S3-совместимое
   хранилище для `output/`-контента, очередь под пайплайн ревью.
