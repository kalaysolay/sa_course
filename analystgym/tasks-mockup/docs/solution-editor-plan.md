# Упрощение редактора решения — 2026-10-18

Цель: пользователь добавляет текст и/или схему без предварительного выбора
между техническими форматами. Количество документов не ограничивается двумя:
все части решения отправляются обоим проверяющим.

## План реализации

1. В «+ Добавить» оставить «Документ» и «Схема»; действия переименования,
   копирования и удаления разместить у соответствующей вкладки.
2. При создании схемы предложить последовательность, процесс и состояния.
   Основной формат — **PlantUML**. Mermaid доступен в дополнительных настройках.
   Добавлять рабочий нейтральный пример с предпросмотром, не ответ на задачу.
3. Сохранить типы `doc`, `plantuml`, `mermaid` и старые черновики. Не выполнять
   автоматическую конвертацию схем. Замена шаблоном требует подтверждения.
4. Проверить полную отправку вкладок, контекст обоих агентов, шаблоны и рендер,
   совместимость с сохранёнными решениями. Обновить спеку, выполнить сборку,
   саморевью, коммит на русском и push.

## Влияние на проверяющих и промпты

`task.js → Api.submitReliable` отправляет `solution.tabs` целиком. Активная вкладка
определяет только отображаемый редактор. Снимок сохраняется в попытке; повтор
отправки с неопределённым исходом использует прежнее полное тело запроса.

`ReviewPipeline.prepare` формирует отдельный user-контекст для каждого агента.
`solutionText` собирает текст **всех** документов (без HTML-оформления) и исходники
**всех** схем. Проверяющие получают исходный код схем, не PNG/SVG-картинку.
Набор критериев разделяется по ролям SA/архитектора, содержимое решения — общее.
Дополнительной копии исходников в JSON нет: размер контекста не удваивается.

Общий серверный контракт, добавляемый к выбранной версии промпта, уточнён:

- рассматривать текст и схемы совместно, замечать противоречия между ними;
- оценивать только собственные критерии по всему решению;
- считать PlantUML и Mermaid равноправными форматами, не требовать оба;
- судить о необходимости схемы по условию/рубрике;
- не засчитывать нейтральный шаблон как проработанное решение задачи.

Не переписываем опубликованные версии промптов в БД и историю проверок.
Итоговые system/user фиксируются в `review_plan`: новый контракт действует
для новых планов, ожидающие задания остаются воспроизводимыми со старым.
Повторная проверка, которая создаёт новый план, получит новый контракт.

Это изменение инструкций, а не доказательство качества LLM. Для утверждений
о точности по-прежнему нужна разметка методиста из `review-calibration.md`.
Демо-движок остаётся явно обозначенным и ограниченным по баллу.

## Границы изменения

Стартовые вкладки задач и собственные сохранённые схемы не мигрируются.
Вкладок может быть несколько; отсутствие текста или схемы само по себе
не запрещает отправку. Интерфейс не вводит новых требований к рубрикам.
Создание схемы и замена её шаблоном — отдельные действия: отмена создания
ничего не добавляет, отмена замены сохраняет собственный код.

## Результат проверки

Пункты 1–4 реализованы. Браузерный сценарий `tests/solution-editor-smoke.html`
проверяет 34 условия, включая рендер всех шести шаблонов, отмену создания
и замены, копирование неактивной вкладки и точное полное тело отправки.
`ReviewPlanTest` проверяет общий контекст двух агентов и раздельные критерии.
Также проходят регрессия отправки, клиентские тесты, Gradle build и
интеграционные проверки PostgreSQL. Реальная модель в этих тестах не вызывается.
