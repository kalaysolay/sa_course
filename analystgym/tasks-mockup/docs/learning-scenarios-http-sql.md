# AnalystGYM — сценарии практики HTTP/REST и SQL

Дата: 2026-11-08. Статус: проект для обсуждения перед спецификацией разработки.

Документ описывает учебные действия, наблюдаемые результаты и восстановление среды. Это не спецификация API, JSON-схем или редактора. Функции ниже предложены, а не объявлены реализованными. Программу курса и контент издательства документ не изменяет.

## 1. Договорённости

- Ресурсы учебных сред, подключения, секреты и политики исполнения находятся в общем серверном конфиге AnalystGYM. Редактор не управляет ими.
- Автор задаёт условие, шаги, стартовый запрос, разрешённые для редактирования поля, подсказки и критерии результата в пределах возможностей зарегистрированного сценария.
- Один блок может содержать несколько шагов с общей рабочей областью. Разнесённые блоки могут продолжать один сценарий, если это явно предусмотрено уроком.
- Выполнение команд доступно аутентифицированному участнику с доступом к материалу; права на конкретную среду проверяются отдельно.
- Вход в AnalystGYM и учебная аутентификация полностью разделены. Токены и cookies платформы не передаются учебным сервисам.
- Состояние связано с участником, контекстом обучения, экземпляром упражнения и запуском. Одного ключа «участник + урок» недостаточно: в уроке может быть несколько упражнений, повторное прохождение и несколько вкладок браузера.
- Условия, фикстуры и проверки имеют версии. Начатое прохождение не меняет их незаметно. Актуальные ограничения безопасности платформы действуют независимо от версии материала.
- Повторные попытки разрешены. Ограничиваются ресурсы и частота, а не возможность учиться после первого успешного вызова.
- «Выполнить» даёт результат операции; «Проверить» фиксирует учебный результат. Ожидаемая ошибка API или SQL может быть успешным выполнением учебного задания.
- Чужие данные, инфраструктура и другие упражнения недоступны. Ошибка ученика в своей среде должна оставаться безопасной для остальных.

## 2. Общий учебный контекст

Основной предметный пример — заявки клиентов. HTTP использует ресурсы `/applications`, `/customers`, `/attachments`. SQL использует таблицы `customers`, `applications`, `application_items`, `attachments`.

Фикстуры включают клиентов без заявок, несколько заявок одного клиента, повторяющиеся значения, NULL, разные статусы и даты, строки без связанных необязательных объектов. Это позволяет проверять смысл запроса, а не только синтаксис.

Одинаковая предметная область не означает автоматической синхронизации HTTP и SQL. Общие данные между инструментами появляются только в явно объявленном сквозном сценарии.

Для каждой строки каталога авторский паспорт дополнительно фиксирует исходное состояние, версию фикстуры, точные ожидаемые ответы и допустимые варианты решения. Статусы ниже — примеры контракта учебного API, не универсальное поведение любого API.

## 3. Знакомство с HTTP и HTTPS

| ID | Сценарий и действие ученика | Наблюдение и проверка | Ошибка или вариация |
|---|---|---|---|
| HTTP-01 | Разобрать URL на схему, host, port, path, query, fragment | Указать части URL; объяснить, что fragment не передаётся серверу в HTTP-запросе | Перепутать query с path; считать fragment серверным параметром |
| HTTP-02 | Изменить разрешённый path и query в адресе учебного API | Сопоставить поля конструктора с фактическим адресом запроса | Произвольная смена host/port не выполняется; учебные альтернативы должны быть зарегистрированы |
| HTTP-03 | Передать пробел, кириллицу, `&`, `+`, повторяющийся query-параметр | Увидеть фактическое кодирование и значение, разобранное сервером | Двойное кодирование; отличие отсутствующего параметра от пустого |
| HTTP-04 | Собрать запрос: метод, адрес, заголовки, тело | Сопоставить элементы с показанным HTTP-представлением | Представление явно обозначено как реконструкция, если это не сетевой захват |
| HTTP-05 | Поменять `Accept` и `Content-Type` | Различить формат отправленного тела и запрошенного ответа | Неподдерживаемый тип: например 415; неподдерживаемое представление: например 406 |
| HTTP-06 | Исследовать код, заголовки и тело ответа | Найти `Location`, `Content-Type`, correlation ID; объяснить ответ 204 без тела | Заголовки запроса и ответа перепутаны; попытка разобрать пустой ответ как JSON |
| HTTP-07 | Сравнить успешное HTTPS-соединение и ошибку сертификата в управляемом стенде | Отличить транспортную ошибку TLS от HTTP-ответа; при ошибке TLS HTTP-статуса нет | В режиме симуляции показывается учебная модель ошибки, а не заявление о реальном TLS-соединении |
| HTTP-08 | Исследовать redirect, HEAD, OPTIONS и границы CORS | HEAD без тела; разрешённые методы по контракту; понимание роли браузера | Вызов через серверный исполнитель не демонстрирует браузерную блокировку CORS; для неё нужен отдельный браузерный стенд |

Служебные заголовки транспорта (`Host`, `Content-Length` и подобные) по умолчанию вычисляет исполнитель. Для обучения их можно показывать; разрешение произвольного изменения потребует отдельного сценария и оценки рисков.

## 4. Методы REST, параметры и тела

| ID | Сценарий и действие ученика | Проверка результата | Ошибка или вариация |
|---|---|---|---|
| REST-01 | GET коллекции без тела | Получена ожидаемая коллекция; состояние не изменилось | Пустая коллекция как корректный результат |
| REST-02 | GET ресурса по PATH ID | Возвращён нужный объект | Несуществующий ID: 404; некорректный формат ID |
| REST-03 | GET с QUERY-фильтрами и сортировкой | Возвращены только нужные объекты в заданном порядке | Несовместимые фильтры; неизвестное поле сортировки |
| REST-04 | Пройти пагинацию | Собраны все ожидаемые ID без пропусков и дублей на фиксированном наборе данных | Выход за последнюю страницу; неправильный размер страницы |
| REST-05 | POST с raw JSON | Создан ровно нужный объект; сохранённые поля верны; изучен Location, если он предусмотрен | Сломанный JSON, отсутствующее поле, неверный тип, бизнес-ошибка |
| REST-06 | POST без тела для операции над ресурсом, например отправки заявки | Нужный переход статуса выполнен по контракту | Переход из недопустимого состояния; лишнее тело |
| REST-07 | Отправить raw text и raw XML в предусмотренные операции | Сервер получил ожидаемые bytes/текст и корректный media type | Несоответствие тела Content-Type; неправильная кодировка; XML здесь не означает SOAP |
| REST-08 | PUT существующего ресурса | Представление заменено по объявленным правилам; изучено поведение пропущенного поля | Отличие замены от частичного изменения; повтор того же PUT |
| REST-09 | PATCH отдельных полей | Изменены только заданные поля, остальные сохранены | Различие отсутствующего поля и null; неподдерживаемый формат patch |
| REST-10 | Сравнить объявленные варианты patch | Выполнено изменение по выбранному контракту: например JSON Merge Patch или JSON Patch | Эти форматы имеют разные тела и Content-Type; нельзя считать их взаимозаменяемыми |
| REST-11 | DELETE ресурса без тела | Целевой объект удалён; соседние сохранены; повторный DELETE исследован | Удаление отсутствующего объекта; запрет удаления по бизнес-правилу |
| REST-12 | Загрузить файл через multipart/form-data вместе с метаданными | Сохранён нужный файл, связь с заявкой и поля формы; сверены размер и контрольная сумма | Неверное имя части; пустой файл; размер выше лимита; недопустимый тип |
| REST-13 | Загрузить binary body и скачать файл | Корректны bytes, Content-Type и предусмотренный Content-Disposition | Отличить binary body от multipart и строки с именем файла |
| REST-14 | Создать заявку, повторить тот же POST с тем же ключом идемпотентности | Два намеренных вызова вернули одну сущность; побочный эффект не продублирован | Тот же ключ с другим телом; новый ключ с тем же телом; срок жизни ключа задаёт сценарий |
| REST-15 | Изменить ресурс с ETag/If-Match | Первый запрос принят, устаревшая версия отклонена по контракту | Конфликт двух изменений; повторное чтение актуальной версии |
| REST-16 | Выполнить асинхронную операцию | Различены принятие запроса и завершение; получен конечный результат через предусмотренный status endpoint | 202 ещё не означает завершение; ошибки обработки после принятия |
| REST-17 | Исследовать задержку, 429 и 5xx | Отличить учебный HTTP-ответ от ограничения платформы; выбрать допустимую стратегию повторения | Таймаут с неизвестным исходом изменения; нельзя автоматически повторять произвольную запись |

Отдельно фиксируется отсутствие тела, пустое тело, `{}` и `null`: для контракта это могут быть разные входы. Тело GET/DELETE не включается как стандартный переносимый способ передачи параметров. Для нестандартного API требуется отдельный явно описанный сценарий.

PUT и DELETE идемпотентны по целевому эффекту, а не по обязательному совпадению статуса каждого ответа. POST может получить идемпотентность через контракт приложения. Для PATCH это свойство зависит от операции.

В multipart boundary формирует исполнитель. Файлы для первых упражнений выдаёт платформа; пользовательская загрузка добавляется отдельным режимом с ограничением хранения и безопасной выдачей вложений.

## 5. Учебная аутентификация и доступ

| ID | Сценарий и действие ученика | Проверка результата | Ошибка или вариация |
|---|---|---|---|
| AUTH-01 | Вызвать публичный endpoint без учебной аутентификации | Запрос успешен при действующей сессии AnalystGYM | Публичность учебного endpoint не открывает гостевой запуск лаборатории |
| AUTH-02 | Вызвать защищённый endpoint без credentials, затем с Bearer | Видны отказ и успешный ответ; отправлено нужное значение Authorization | Отсутствующий, некорректный, истёкший или отозванный токен |
| AUTH-03 | Выполнить Basic-аутентификацию | Конструктор формирует Basic из учебных username/password | Неправильный пароль; Base64 не является шифрованием; используются только учебные данные |
| AUTH-04 | Использовать API key | Ключ передан в предусмотренном контрактом месте | Неверное имя заголовка; отсутствующий/отозванный ключ; query-ключ только в явно предусмотренном учебном контракте |
| AUTH-05 | Сравнить недостаточный scope и отсутствие действительных credentials | Различены предусмотренные контрактом 401 и 403 | Действующий токен сам по себе не гарантирует разрешения на операцию |
| AUTH-06 | Получить OAuth-токен через Client Credentials и вызвать API | Получен ограниченный учебный токен; видны scope и срок действия | Неверный client secret, неподдерживаемый scope; это не вход пользователя |
| AUTH-07 | Пройти Authorization Code + PKCE | Пройдены переход, согласие, callback, обмен кода и вызов API | Неверный verifier/redirect URI/state; повторный обмен кода отклонён |
| AUTH-08 | Обновить токен или проверить истечение/отзыв | Доступ меняется согласно контракту учебного сервера | Refresh доступен только тем клиентам и flow, где он предусмотрен; после reset старые credentials не дают доступ к новой среде |

Bearer/Basic/API key — способы предъявления credentials. OAuth — протокол делегирования доступа и получения токенов; учебный вход пользователя через OIDC при необходимости оформляется отдельным расширением.

Для одного упражнения необязательно открывать все способы аутентификации. Зарегистрированный сценарий определяет доступные способы, а автор выбирает подходящий учебный сценарий. Реальные производственные ключи участников не используются.

## 6. SQL: чтение

| ID | Сценарий и действие ученика | Проверка результата | Ошибка или вариация |
|---|---|---|---|
| SQL-01 | SELECT нужных столбцов и алиасы | Совпадают поля и значения результата | SELECT * вместо заданных полей; неверный алиас |
| SQL-02 | WHERE, AND/OR, IN, BETWEEN, LIKE | Выбраны нужные строки с учётом приоритета условий | Ошибка скобок и граничных значений |
| SQL-03 | NULL, IS NULL, COALESCE | Правильно обработаны пропуски | Сравнение `= NULL`; отличие NULL от пустой строки и нуля |
| SQL-04 | ORDER BY, LIMIT/OFFSET | Порядок устойчив по заданным ключам, включая разрешение равных значений | LIMIT без определённого порядка не гарантирует конкретную страницу |
| SQL-05 | INNER JOIN | Получены нужные связанные записи | Декартово произведение; ошибочный ключ; размножение строк |
| SQL-06 | LEFT JOIN и поиск отсутствующей связи | Сохранены объекты без пары | Фильтр правой таблицы в WHERE меняет результат внешнего соединения |
| SQL-07 | JOIN нескольких таблиц | Верны связи и итоговая кратность | Суммы задвоены из-за связи один-ко-многим |
| SQL-08 | COUNT/SUM/AVG/MIN/MAX, GROUP BY, HAVING | Верны группы, агрегаты и фильтрация групп | COUNT(*) против COUNT(column); WHERE против HAVING |
| SQL-09 | DISTINCT и UNION/UNION ALL | Дубликаты сохранены или удалены согласно условию | Скрытие ошибочного JOIN через DISTINCT |
| SQL-10 | Подзапросы, EXISTS и CTE | Получен нужный набор данных | Подзапрос возвращает несколько строк; NOT IN с NULL |
| SQL-11 | CASE, даты и интервалы | Верны классификация и границы периода | Часовой пояс и контрольная дата зафиксированы фикстурой |
| SQL-12 | Оконные функции | Корректны ранги, выбор последней заявки, итоги по окну | Равные значения, partition, frame и отличие от GROUP BY |

Проверка SELECT сравнивает значения, типы и кратность строк; порядок — только если он входит в условие. Числовая точность, допустимые алиасы и политика сравнения NULL фиксируются заранее. Дополнительные фикстуры проверяют обобщаемость решения. Если цель — именно JOIN или GROUP BY, одного совпадения результата мало: отдельно проверяется учебное требование к конструкции, без требования точного текста запроса.

### 7.1. CREATE TABLE: ограничивать объекты, а не первую успешную команду

Предложение «не более одного успешного вызова» не принимается как общее правило. Оно мешает исправить неверную структуру и не ограничивает число объектов, созданных одним сложным вызовом. Для разных уроков может требоваться несколько таблиц.

Предлагаемый учебный режим:

1. Участник получает личную рабочую среду данного упражнения и запуска. Не создаём её при простом просмотре статьи.
2. Сценарий задаёт конечный набор ожидаемых объектов: например только `application_notes`, либо `applications` и `application_items`.
3. Среда допускает создание только в разрешённой области; запрещены создание БД, ролей, расширений, функций, триггеров и произвольные внешние подключения. Дополнительные возможности включаются отдельными сценариями.
4. Платформа ограничивает число объектов, столбцов, индексов, объём данных, время и число активных сред. Значения берутся из общего конфига.
5. Неверная, но синтаксически успешная таблица не завершает упражнение. Участник исправляет её разрешённой командой либо сбрасывает среду и пробует снова.
6. После достижения лимита объектов повторная попытка возможна через reset с отдельным ограничением частоты. Не создаётся новая бесконтрольная среда на каждый клик.
7. Проверка исследует итоговую схему и при необходимости выполняет контрольные вставки в отдельной проверочной копии/откатываемом контексте.

Численные квоты и механизм строгого ограничения объектов предстоит определить в спецификации. Простая проверка префикса SQL и последующий подсчёт таблиц не являются достаточной защитой: нужно учитывать конкурентные команды, неявные объекты и побочные эффекты.

### 7.2. UPDATE/DELETE: целевая строка плюс контрольные строки

Для базового DELETE среда заранее содержит целевую строку и несколько контрольных строк. Участник удаляет строку по условию. Проверяется не только отсутствие цели, но и сохранность остальных данных и связей.

Если создать ровно одну видимую строку, `DELETE FROM applications` ошибочно будет выглядеть правильным решением. Несколько строк делают результат содержательным. Аналогично проверяется UPDATE.

Предпочтительный режим первых упражнений — личная копия небольшого набора данных. Ошибка без WHERE может испортить только эту копию; участник увидит последствия и выполнит reset. Основные данные платформы не затрагиваются.

Общая таблица с пользовательскими строками рассматривается только как отдельный вариант реализации. Одного пользовательского WHERE для изоляции недостаточно: нужны принудительные права и, если выбран этот путь, корректная политика строкового доступа. Схема PostgreSQL сама по себе также не является жёсткой границей доступа и ресурсов.

### 7.3. Сохранение состояния

- Для одиночного упражнения используется восстанавливаемая фикстура; между «Выполнить» и «Проверить» результат сохраняется.
- Для цепочки INSERT → UPDATE → SELECT → DELETE используется одна личная сессия с явной последовательностью шагов.
- Транзакционное упражнение удерживает одно соединение на ограниченное время и не переносит случайно BEGIN/COMMIT между разными соединениями пула.
- Успешная проверка сохраняет снимок результата. Последующий reset не стирает историю попытки.
- После технического отказа нельзя автоматически повторять изменяющий SQL с неизвестным исходом. Сначала выясняется состояние либо предлагается восстановление фикстуры.
- Ограничение времени выполняется и внутри БД, и внешним исполнителем. Пользовательский SQL не должен уметь снять обязательный внешний deadline.

## 8. Сквозные паспорта для проверки полноты модели

### FLOW-01. POST и идемпотентность — один блок, несколько шагов

Начало: пустой набор заявок личной среды, публичный учебный endpoint, вход в AnalystGYM обязателен.

1. Собрать POST с телом и ключом идемпотентности, выполнить его, сохранить ID.
2. Повторить тот же запрос с тем же ключом отдельным намеренным действием.
3. Убедиться в совпадении ID и единственном созданном объекте.
4. Изменить тело, оставив ключ, исследовать предусмотренный контрактом конфликт.
5. По желанию повторить с новым ключом и объяснить создание другого объекта.

Проверка: история двух намеренных действий и состояние среды; одного совпадения ответов недостаточно. Внутренний ID операции платформы не смешивается с учебным ключом идемпотентности. Reset восстанавливает заявки и реестр учебных ключей, не удаляя проверенные попытки.

### FLOW-02. Файл и учебная аутентификация

Начало: личная заявка, выданный небольшой учебный файл, защищённый endpoint вложений.

1. Выполнить загрузку без credentials, получить предусмотренный отказ.
2. Настроить нужный способ аутентификации, отправить multipart с файлом и метаданными.
3. Получить attachment ID, скачать файл, сопоставить контрольную сумму.
4. Исследовать неверное имя части либо превышение учебного размера файла.

Проверка: принадлежность вложения заявке, содержимое файла и отсутствие лишних вложений. Файлы имеют срок хранения; reset удаляет личные учебные вложения. Ответ 401 учебного API не завершает вход в AnalystGYM.

### FLOW-03. SQL CREATE TABLE с исправлением

Начало: личная пустая область, разрешена одна таблица `application_notes` и её ограниченный набор сопутствующих объектов; общий лимит задаёт платформа.

1. Создать таблицу с ID, ссылкой на заявку, текстом и временем создания по заданной модели.
2. Проверить структуру; при неверной структуре получить объяснение, сохранив возможность исправления.
3. При необходимости сбросить среду и создать исправленный вариант.
4. Выполнить контрольный INSERT и SELECT, если они входят в профиль упражнения.

Проверка: обязательные свойства схемы и ограничения. Вторая произвольная таблица отклоняется/не допускается к исполнению; первый успешный CREATE неправильной структуры не блокирует обучение навсегда. Попытка создать большое число объектов не обрабатывается как обычное безлимитное упражнение.

### FLOW-04. SQL DELETE с ошибкой и восстановлением

Начало: несколько личных заявок; только одна подходит под условие удаления.

1. Найти цель через SELECT.
2. Выполнить DELETE с условием.
3. Проверить отсутствие цели и сохранность контрольных данных.
4. В учебной вариации выполнить слишком широкий DELETE, получить объяснение последствий и восстановить фикстуру.

Проверка результата первой попытки сохраняется отдельно. Восстановление возвращает только среду этого упражнения. Ошибочный DELETE не затрагивает другого участника.

### FLOW-05. Общий HTTP → SQL — последующее расширение

Начало: явно связанная личная среда API и БД; авторский сценарий объявляет момент появления записи в SQL.

1. Создать заявку через API.
2. Найти созданный ID через SQL.
3. Изменить разрешённое поле через API и прочитать его в БД.
4. Объяснить задержку, если сценарий предусматривает асинхронное обновление.

Проверка связывает действия через ID одной сущности. Согласованность данных и права прямой записи в БД требуют отдельного решения. Независимые HTTP/SQL-сценарии не объявляются связанными автоматически.

## 9. Пользовательские и отказные сценарии для всех инструментов

| ID | Ситуация | Ожидаемое поведение |
|---|---|---|
| RUN-01 | Первый запуск, выход и возвращение | Создание среды по требованию; восстановление до истечения срока жизни; истечение объясняется явно |
| RUN-02 | Несколько вкладок и конкурирующие действия | Операции одной среды упорядочены либо конфликт явно отклонён; чужие результаты не перезаписываются |
| RUN-03 | Повтор сетевой доставки одной команды | Одинаковый внутренний operation ID не выполняет изменение повторно; новое нажатие — отдельное действие |
| RUN-04 | Reset при выполняющейся операции | Старые операции останавливаются; запоздалый результат не попадает в новое поколение среды |
| RUN-05 | Нет входа, истёк доступ к уроку, указан чужой session ID | Сервер отказывает в выполнении, просмотре, проверке и reset; состояние не раскрывается |
| RUN-06 | Исчерпана квота, очередь заполнена, стенд недоступен | Понятная техническая причина, возможность повторить по правилам платформы; учебная оценка не снижается |
| RUN-07 | Таймаут, сбой исполнителя, потерян ответ после записи | Состояние «исход неизвестен» допустимо; изменение не повторяется автоматически |
| RUN-08 | Истёк срок жизни среды или credentials | Безопасная очистка; предложено начать новый запуск; история проверенных результатов сохранена |
| RUN-09 | Автор обновил урок или фикстуру | Начатый запуск остаётся воспроизводимым; переход на новую редакцию явный |
| RUN-10 | Попытка обойти назначения, права, SQL-профиль или лимиты | Платформа отклоняет действие независимо от JSON клиента; фиксируется безопасная диагностика без секретов |

Для реальных HTTP/SQL-операций выполнение допускается только после проверки серверной конфигурации. Секреты и скрытые проверки не включаются в публичный документ статьи. Ограничиваются также reset, выдача токенов, загрузка файлов и чтение статуса.

## 10. Граница будущей спецификации

До редактора нужно определить:

1. Состав первого выпуска из каталога и конкретные учебные контракты endpoint/фикстур.
2. Паспорта сценариев и формат ссылок из блоков, включая версии и правила совместного состояния.
3. Разделение публичного контента, закрытых проверок и общего конфигурационного файла платформы.
4. Изоляцию SQL для чтения, DML и DDL; строгие квоты объектов/хранения и гарантированную остановку операций.
5. Модель запуска, операции, проверки, reset и очистки; ошибки с известным и неизвестным исходом.
6. Механизм реальной и симулированной HTTP-аутентификации; браузерный стенд для OAuth/CORS/TLS там, где нужен именно браузер.
7. Проверку результата и учебного способа решения; форматы обратной связи и историю попыток.
8. Проверки конкурентности, восстановления, отсутствия доступа к чужим средам и сохранности инфраструктуры.

Предлагаемая последовательность: сначала базовые HTTP/REST и способы предъявления credentials, SQL SELECT/DML с личными фикстурами и ограниченный CREATE TABLE; затем OAuth flows, расширенные HTTP-кейсы, транзакции и сквозные среды. Это предмет выбора объёма, а не утверждённый план разработки.

SOAP и брокеры сообщений требуют следующих каталогов; здесь они не считаются проработанными.

## 11. Источники для последующей спецификации

- [HTTP Semantics — RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html): URL fragment, методы, тела, идемпотентность, коды и заголовки. Фактический учебный контракт фиксируется в паспорте.
- [PATCH — RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html): частичные изменения; формат patch описывается отдельно.
- [PostgreSQL 16: Schemas](https://www.postgresql.org/docs/16/ddl-schemas.html): схемы, search_path и ограничения изоляции через права.
- [PostgreSQL 16: Privileges](https://www.postgresql.org/docs/16/ddl-priv.html): права операций и владение объектами.
- [PostgreSQL 16: Client Connection Defaults](https://www.postgresql.org/docs/16/runtime-config-client.html): таймауты и режимы транзакций.
- [OAuth Security BCP — RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html): ограничения безопасных OAuth flows.

Документ подготовлен без изменения поведения приложения. Проверка сборки потребуется при реализации сценариев и контрактов.
